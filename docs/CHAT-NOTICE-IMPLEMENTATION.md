# 채팅·여행 공지 구현 정리

> 기준일: 2026-10-25 · 서버·클라이언트 구현 및 연결된 WeGoTrip DB 적용 완료

## 1. 구현 범위

| 구분      | 구현 내용                                                     |
| --------- | ------------------------------------------------------------- |
| 채팅      | 여행 전체·파티별 실시간 대화, 과거 메시지 조회                |
| 이미지    | 여러 사진 선택·일괄 전송, Cloudinary 저장, 이미지 메시지 필터 |
| 투표      | 단일·복수 선택, 여행 장소 연결, 자동·수동 마감                |
| 여행 공지 | 방장 전용 작성·수정·삭제·고정, 멤버 전체 조회                 |
| 푸시      | 새 채팅·이미지·투표·공지 알림, 알림 클릭 시 해당 화면 이동    |
| 공통 처리 | 서버 권한 검사, 중복 요청 방지, 푸시 실패 재시도              |

실제 서비스 기능은 **HTTP 모드**에서 제공한다. 체험용 `mock` 모드는 기기 내 데이터를 사용하며 실시간 공유·이미지·투표·FCM 발송은 제공하지 않는다.

## 2. 채팅

### 화면과 실시간 대화

- 채팅방은 **전체 채팅**과 **내가 참여 중인 파티 채팅**으로 나뉜다.
- 상단 드롭다운으로 채팅방을 변경한다. 채팅방 선택 영역과 대화 스크롤을 분리해 긴 대화에서도 방을 바꿀 수 있다.
- 텍스트는 최대 **2,000자**다. 최신 50개를 먼저 표시하고 이전 대화를 추가로 불러온다.
- WebSocket으로 변경을 전달하고, HTTP로 메시지·투표의 최신 내용을 조회한다.
- 연결 중단 시 재접속하며 주기적 조회로 놓친 변경을 복구한다.

### 이미지 전송

1. 입력창의 첨부 버튼에서 사진 선택 패널을 연다.
2. 기기 사진 목록에서 여러 장을 선택하고 전송 버튼을 누른다.
3. 선택한 순서대로 백엔드 업로드 → Cloudinary 저장 → DB에 URL·업로드 정보 저장 → 이미지 메시지 생성을 수행한다.

사진마다 메시지 1개가 생성된다. 실패한 사진은 선택을 유지하며, 응답 유실 후 재시도할 때 기존 업로드 ID와 요청 키를 재사용한다. 사진을 눌러 확대할 수 있고, 채팅방 선택기 오른쪽의 이미지 필터를 켜면 이미지 메시지만 조회한다.

| 항목           | 동작                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| 지원 형식·크기 | JPG·PNG·WebP·GIF, 서버 기준 파일당 최대 8MiB                                |
| 네이티브 사진  | 최근 사진을 하단 패널에 표시하고 추가 목록을 불러옴                         |
| 웹 사진        | 파일 선택기로 가져온 사진을 패널에서 선택                                   |
| 웹 자동 압축   | 8MiB 초과 정지 사진을 긴 변 최대 2,560px로 축소하고 품질·크기를 조절해 전송 |
| 형식 변환      | 네이티브의 HEIC 등 미지원 형식·큰 정지 이미지를 JPEG로 변환·축소            |
| 저장 위치      | 이미지 파일은 Cloudinary, URL과 참조 정보는 DB                              |

업로드한 사용자와 채팅방이 일치하는 이미지만 메시지에 첨부할 수 있다.

웹은 8MiB 이하의 사진을 원본으로 전송한다. 큰 JPEG는 JPEG로 압축하고 PNG·WebP는 투명 배경을 보존해 WebP로 압축한다. WebP 인코딩 미지원 브라우저는 PNG로 처리한다. EXIF 방향과 가로세로 비율을 유지하며, GIF와 애니메이션 PNG·WebP는 움직임을 보존하기 위해 자동 압축하지 않고 8MiB 이하 원본만 전송한다.

### 투표

질문은 최대 **200자**, 항목은 **2~10개**, 항목 이름은 최대 **150자**다.

| 옵션      | 기본값 | 동작                                               |
| --------- | ------ | -------------------------------------------------- |
| 장소 연결 | OFF    | 활성화하면 항목마다 여행에 저장된 장소를 연결      |
| 복수 선택 | OFF    | OFF는 1인 1표, ON은 여러 항목에 각각 한 표씩 선택  |
| 자동 마감 | OFF    | 활성화하면 빠른 시간 선택 또는 날짜·시간 직접 입력 |

선택한 항목을 다시 누르면 취소된다. 복수 선택에서도 같은 항목에 중복 투표할 수 없으며, 참여 인원은 사람별로 한 번만 집계한다. 항목별 비율은 참여 인원 기준이므로 복수 선택에서는 합계가 100%를 넘을 수 있다.

마감 시간과 남은 시간을 표시하며 서버가 마감 시각을 최종 판단한다. 작성자 또는 해당 채팅방에 접근 가능한 방장은 수동으로 마감할 수 있다. 마감한 투표는 다시 열 수 없고 생성 후 항목·선택 모드도 고정된다. 연결한 장소가 삭제돼도 생성 당시 장소 이름·주소는 보존한다.

## 3. 여행 공지

| 기능                | 권한·동작                                                   |
| ------------------- | ----------------------------------------------------------- |
| 작성·수정·삭제·고정 | 현재 여행장(방장)만 가능                                    |
| 목록·본문 조회      | 현재 여행 멤버 모두 가능                                    |
| 입력 제한           | 제목 100자, 본문 3,000자                                    |
| 목록 정렬           | 고정 공지 우선, 최신순. 여러 공지 고정 가능                 |
| 고정 공지 접근      | 공지 목록·여행 개요·서버 채팅 화면에서 제공                 |
| 수정 충돌           | 버전이 오래된 저장·삭제 요청을 거절하고 최신 내용 확인 안내 |

공지는 서버 DB에 저장해 다른 멤버·기기에서도 조회할 수 있다. **목록 진입·앱 복귀·새로고침 때 갱신**하며, 공지 전용 실시간 소켓은 추가하지 않았다.

새 공지를 등록하면 다른 멤버에게 푸시를 예약한다. 수정·고정 변경·삭제는 추가 푸시를 만들지 않는다. 기존 기기에만 저장된 공지는 원본을 보존하고 서버에 자동 업로드하거나 공유 목록에 섞지 않는다.

## 4. 접근 권한과 데이터 보호

| 상황             | 처리                                                       |
| ---------------- | ---------------------------------------------------------- |
| 전체 채팅 접근   | 현재 여행 멤버만 조회·작성·구독 가능                       |
| 파티 채팅 접근   | 현재 해당 파티 멤버만 가능. 방장도 파티 밖에서는 접근 불가 |
| 공지 관리        | 프런트엔드와 서버 모두 방장 권한 검사                      |
| 멤버·파티 탈퇴   | 접근 권한을 다시 검사해 이후 조회·구독·알림 차단           |
| 종료·보관된 여행 | 채팅·공지 조회만 허용, 작성·투표 변경·공지 관리 차단       |

모든 API는 기존 JWT 인증을 사용한다. 작성자와 작성 시각은 서버가 결정하며, WebSocket 이벤트에도 실제 대화 원문을 싣지 않고 인증된 API로 다시 조회한다.

## 5. 채팅·공지 공통 푸시

### 발송 조건

| 발생한 동작                              | 알림 종류      | 수신 대상                       |
| ---------------------------------------- | -------------- | ------------------------------- |
| 새 텍스트·이미지·투표 메시지             | `CHAT_MESSAGE` | 해당 전체·파티 채팅의 현재 멤버 |
| 새 여행 공지                             | `TRIP_NOTICE`  | 현재 여행 멤버                  |
| 투표 참여·취소·마감, 공지 수정·고정·삭제 | 발송 없음      | —                               |

작성자 자신의 모든 기기는 제외한다. 등록 기기가 있고 계정의 푸시 설정이 켜진 멤버만 대상으로 하며, 공지는 기존 여행별 알림 설정도 확인한다.

### 발송 흐름

```text
채팅·공지 저장 + 수신 대상 기록 → 커밋
→ 기기별 발송 대기 생성 → 현재 권한·설정 재확인 → FCM 전송
→ 알림 클릭 → 로그인 계정 확인 → 해당 채팅방·공지 화면 이동
```

- 원본 저장과 수신 대상 기록은 같은 트랜잭션으로 처리한다. 기기별 대기 생성과 FCM 호출은 채팅·공지 저장 후 수행한다.
- 발송 직전에 멤버십·계정 상태·알림 설정·기기 토큰을 재검사한다. 삭제된 공지의 미발송 작업도 건너뛴다.
- 실패 시 재시도하며 기본 유효기간은 **24시간**, 최대 시도 수는 **7회**다. 작업 중 서버가 중단되면 임대 만료 후 다른 작업자가 이어받는다.
- FCM이 명시적으로 등록 해제된 토큰이라고 응답했을 때만, 기존 토큰 일치를 확인하고 기기 등록을 정리한다.
- 잠금 화면에는 기본 안내만 표시하며 대화·공지 원문, 작성자 이름, 이미지 URL은 보내지 않는다.
- 앱 실행 중 알림, 백그라운드·종료 후 알림 열기, 웹 알림·서비스 워커 클릭을 처리한다.

`SENT`는 **FCM 접수 완료**를 뜻하며 기기 표시·열람 확인은 아니다. 외부 전송 후 응답이 유실되면 중복 전달이 가능하며, 클라이언트는 발송 ID로 중복 표시·열기를 줄인다.

## 6. 저장 구조와 DB 적용 상태

| 테이블                                            | 역할                                             |
| ------------------------------------------------- | ------------------------------------------------ |
| `chat_message`, `chat_image_upload`               | 채팅 메시지와 Cloudinary 이미지 참조             |
| `chat_poll`, `chat_poll_option`, `chat_poll_vote` | 투표·항목·사용자 선택                            |
| `trip_notice`                                     | 여행 공지 원문·고정 여부·수정 버전               |
| `push_event`, `push_delivery`                     | 공통 푸시 이벤트·대상 기록·기기별 발송 및 재시도 |
| 기존 회원·여행·파티·기기·설정 테이블              | 인증·멤버십·수신 대상 및 알림 설정               |

현재 연결된 WeGoTrip DB에는 채팅 기반 구조와 **012 자동 마감, 013 복수 선택, 014 푸시, 015 여행 공지** 적용을 완료했다. 승인된 변경만 적용했으며 기존 데이터를 보존했다.

다른 DB를 준비할 때는 `backend/db/migrations/`의 스크립트를 확인한다. 채팅 기반은 **신규 DB의 010**과 **기존 WeGoTrip 구조용 011** 중 상황에 맞는 경로를 사용하고, 이후 012~015를 적용한다. 010·011을 무조건 함께 순서대로 실행하는 방식은 아니다. 애플리케이션이 마이그레이션을 자동 실행하지 않는다.

기존 `notification`은 개인 알림용 테이블이며 이번 여행 공지 저장에 사용하지 않는다. 앱 내 개인 알림함 API와 서비스 전체 공지 발송 기능은 후속 구현 범위다.

## 7. 주요 API

채팅 기본 경로: `/api/v1/trips/{tripId}/chat`  
파티 채팅은 각 요청에 `?partyId={partyId}`를 전달하며 생략하면 전체 채팅이다.

| 메서드 | 하위 경로                     | 용도                                                        |
| ------ | ----------------------------- | ----------------------------------------------------------- |
| GET    | `/messages`, `/messages/{id}` | 목록·단건 조회. 목록은 `before`, `limit`, `imagesOnly` 지원 |
| POST   | `/messages`                   | 텍스트·이미지 메시지 생성                                   |
| POST   | `/images`                     | multipart 이미지 업로드                                     |
| POST   | `/polls`                      | 투표 생성                                                   |
| PUT    | `/polls/{id}/vote`            | 항목 선택·취소                                              |
| PUT    | `/polls/{id}/closure`         | 수동 마감                                                   |

공지 기본 경로: `/api/v1/trips/{tripId}/notices`

| 메서드 | 하위 경로                   | 용도                                          |
| ------ | --------------------------- | --------------------------------------------- |
| GET    | 기본 경로, `/{id}`          | 목록·단건 조회. 목록은 `cursor`, `limit` 지원 |
| POST   | 기본 경로                   | 공지 생성: `title`, `body`, `pinned`          |
| PUT    | `/{id}`                     | 공지 수정: 생성 필드 + `expectedVersion`      |
| DELETE | `/{id}?expectedVersion=...` | 공지 삭제                                     |

채팅 메시지·투표 생성과 공지 생성·수정·삭제는 UUID `Idempotency-Key` 헤더가 필요하다. 같은 키와 입력을 재사용해 응답 유실로 인한 중복 저장을 막는다. ID와 변경 버전은 큰 정수의 정밀도를 보존하는 문자열로 전달한다.

실시간 채팅은 `/ws/chat`을 사용한다. HTTPS 배포에서는 `wss://`를 사용하고 프록시에서 WebSocket Upgrade를 전달해야 한다.

## 8. 실행 방법

### 환경 설정

기존 DB 연결 설정과 함께 `backend/.env`를 준비한다.

```dotenv
CLOUDINARY_CLOUD_NAME=your_cloud_name
CLOUDINARY_API_KEY=your_api_key
CLOUDINARY_API_SECRET=your_api_secret
users.allowed-origins=http://localhost:8081,http://localhost:8082

PUSH_ENABLED=true
FIREBASE_PROJECT_ID=your_firebase_project_id
FIREBASE_CREDENTIALS_FILE=
```

서버 Firebase 인증은 ADC 또는 `FIREBASE_CREDENTIALS_FILE`에 지정한 서비스 계정 파일을 사용한다. 배포 서버에도 별도로 인증을 설정해야 한다. Cloudinary 비밀 키와 Firebase 서버 인증 키는 클라이언트에 넣지 않는다.

`frontend/.env.local`의 기본 연결 설정:

```dotenv
EXPO_PUBLIC_DATA_SOURCE=http
EXPO_PUBLIC_API_URL=http://localhost:8080/api
```

### 실행

```powershell
# 터미널 1: backend 폴더
./gradlew.bat bootRun

# 터미널 2: frontend 폴더
npm ci
npm run web -- --port 8082
```

Android/iOS는 Firebase 설정 파일이 포함된 **네이티브 개발 빌드**가 필요하다. Expo Go는 FCM을 지원하지 않는다. 새 네이티브 모듈·권한을 반영하려면 Android는 `npm run android`, iOS는 macOS에서 `npm run ios`로 다시 빌드한다. 실제 휴대폰에서는 API 주소의 `localhost`를 휴대폰에서 접근 가능한 서버 주소로 바꾼다.

푸시 수신에는 **기기 등록 + OS/브라우저 알림 권한 + 내 정보의 푸시 알림 설정**이 모두 필요하다. Android는 `google-services.json`, iOS는 Firebase 설정 파일과 APNs 연결, 웹은 Firebase 웹 설정·VAPID 공개키 및 HTTPS/localhost가 필요하다.

위 결과는 2026-10-25의 최근 구현 검증 기록이다. 자동 테스트는 격리된 H2와 Cloudinary·FCM 대역을 사용했다. 네이티브 번들 생성 통과는 APK·IPA 설치 빌드나 실기기 수신 검증을 의미하지 않는다.

웹 자동 압축은 추가로 로컬 Chrome에서 검증했다. 약 12.8MB의 고해상도 JPEG가 약 2.6MB로 줄어드는 것을 확인했고, EXIF 세로 방향·투명 배경·브라우저 대체 처리·임시 URL 정리도 통과했다. 합성 이미지만 사용했으며 외부 업로드는 수행하지 않았다.

운영 확장 시 필요한 작업:

- 서버 여러 대에서 즉시 채팅 이벤트를 공유하려면 Redis Pub/Sub 등의 공통 전달 계층 추가.
- 미사용 Cloudinary 업로드와 오래된 푸시 기록의 보관·자동 정리 정책 마련.
- 서비스 전체 공지·개인 알림함을 추가할 때 기존 공통 발송 모듈과 종류별 정책 재사용.
