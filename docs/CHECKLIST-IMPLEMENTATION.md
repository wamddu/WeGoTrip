# 준비물 기능 구현

작성일: 2026-10-02

권한 수정일: 2026-10-09. 배정된 준비물의 완료 체크·취소를 담당자만 할 수 있도록 수정했다. DB 스키마와 기존 데이터는 변경하지 않았다.

전체 멤버 준비물 변경: 2026-10-09. 신규 공용 등록은 모든 현재 멤버에게 개인 항목을 하나씩 생성하며 각자의 완료 상태를 따로 저장한다.

기존 공용 지원 제거: 2026-10-09. 기존 공용 데이터는 사용자가 삭제하는 전제로 ‘이전 공용’ 목록·필터·안내와 편집 전환 화면을 제거했다. 코드 변경 과정에서 실제 DB 데이터를 삭제하거나 스키마를 변경하지 않았다.

## 구현 범위

여행 준비물을 서버에 저장하고 여행 멤버가 함께 조회·관리하도록 연결했다. **기존 `packing_item` 테이블을 사용하며 실제 DB 스키마와 데이터는 변경하지 않았다.** 새 마이그레이션도 없다.

- 이름·담당자 추가/수정, 삭제
- 모든 멤버가 각자 챙길 준비물 일괄 등록 또는 특정 멤버에게 개인 등록
- 완료 체크와 완료 취소
- 전체·내 준비물·미완료 필터, 담당자 선택과 멤버별 준비 현황
- 준비물 목록·여행 개요·홈에서 같은 데이터로 진행률 계산
- 중복 요청 방지, 동시 수정 충돌 안내, 기존 기기 데이터 원본 보존

‘내 준비물’은 본인이 담당하는 **공유 항목의 필터**다. 개인 비공개 항목이 아니며 모든 여행 멤버가 담당자별 준비 상태를 조회할 수 있다. 완료 체크·취소는 해당 담당자만 할 수 있다. 이름·담당자 수정과 삭제는 기존 공동 관리 권한을 유지하며 변경은 해당 개인 항목에만 적용된다.

예를 들어 멤버 4명이 참여한 여행에서 ‘모든 멤버가 각자 준비’를 선택해 여권을 등록하면 담당자가 각각 다른 준비물 4개가 생성된다. A가 자신의 여권을 체크해도 B·C·D의 항목은 미완료로 남는다. 같은 이름의 항목을 하나의 완료 상태로 합치지 않는다.

## DB 매핑

| 기존 컬럼 | 역할 |
| --- | --- |
| `id` | 준비물 ID. API에서는 문자열로 전달 |
| `trip_id` | 소속 여행 |
| `owner_trip_member_id` | 개인 항목의 담당 멤버. 기존 공용 기록이나 담당자 탈퇴 시 NULL |
| `title` | 이름, 앞뒤 공백 제거 후 1~150자 |
| `done` | 준비 완료 여부 |

API의 `ownerId`는 사용자 ID다. 서버는 같은 여행의 현재 활성 멤버인지 검증한 뒤 `trip_member.id`로 변환한다. 멤버가 정상 탈퇴하면 기존 FK의 `ON DELETE SET NULL`에 따라 준비물이 공용으로 바뀌고 완료 상태는 유지된다. 지출·정산 참조에 따른 기존 탈퇴 제한은 유지한다.

전체 등록은 여행 잠금 안에서 읽은 현재 활성 멤버의 목록을 사용한다. 별도 테이블이나 그룹 ID를 추가하지 않고 기존 테이블에 개인 행을 저장한다. 등록 후 여행에 새로 참여한 멤버에게 기존 항목을 자동 추가하지 않으며, 필요한 준비물은 해당 멤버에게 별도로 등록한다.

수량·메모·분류·파티 연결·변경 이력 저장은 이번 범위에 포함하지 않는다.

## API

기본 경로: `/api/v1/trips/{tripId}/packing-items`

Bearer JWT 인증과 기존 `ApiResponse` JSON 형식을 사용한다. 응답은 `Cache-Control: no-store`를 적용한다.

| 메서드 | 하위 경로 | 요청 | 응답 |
| --- | --- | --- | --- |
| GET | 기본 경로 | `cursor`, `limit` 선택 | `items`, `nextCursor`, `checklistStateToken` |
| GET | `/{itemId}` | 없음 | 준비물 단건 |
| POST | 기본 경로 | `title`, `ownerId` | `{ items: [...] }`, 201. NULL이면 현재 멤버 전체, 개인 ID면 1개 |
| PUT | `/{itemId}` | `title`, `ownerId`, `expectedStateToken` | 수정한 준비물 |
| PUT | `/{itemId}/completion` | `done`, `expectedStateToken` | 완료 상태를 변경한 준비물 |
| DELETE | `/{itemId}` | query의 `expectedStateToken` | `{ deletedId }` |

모든 변경 요청은 UUID 형식의 `Idempotency-Key` 헤더가 필수다.

개인 항목 응답 예시:

```json
{
  "id": "123",
  "title": "여권",
  "ownerId": "101",
  "done": false,
  "stateToken": "<64자리 SHA-256 해시>"
}
```

신규 등록의 완료 상태는 `false`다. 이름·담당자 수정 API는 완료 상태를 변경하지 않고, 완료 API는 이름·담당자를 변경하지 않는다. 완료 값은 boolean만 허용하고 정의되지 않은 요청 필드는 거절한다.

신규 전체 등록은 모든 개인 항목과 중복 요청 응답을 하나의 트랜잭션으로 저장한다. 중간에 실패하면 모든 삽입을 롤백한다. 같은 키·입력으로 재시도하면 최초 등록 당시의 항목 배열을 반환하며 멤버 수가 이후 달라져도 다시 생성하지 않는다.

수정 요청의 `ownerId`는 개인 담당자 ID가 필수다. 기존 항목을 담당자 없는 한 개의 공용 항목으로 바꾸는 요청은 `400 PACKING_ASSIGNMENT_REQUIRED`로 거절한다. 기존 개인 항목의 완료 상태는 내용 수정으로 바뀌지 않지만, 담당자가 없는 이전 공용 기록을 개인에게 배정할 때는 누가 챙겼는지 확인할 수 없으므로 미완료부터 시작한다.

여행 비멤버는 `404 TRIP_NOT_FOUND`, 다른 여행의 항목은 `404 PACKING_ITEM_NOT_FOUND`, 잘못된 담당자는 `400 PACKING_MEMBER_NOT_IN_TRIP`으로 처리한다. 보관 여행은 조회할 수 있고 신규 변경은 `409 TRIP_ARCHIVED`로 막는다.

배정된 준비물의 담당자가 아닌 멤버가 완료·취소를 요청하면 `403 PACKING_OWNER_REQUIRED`로 거절한다. 여행장도 본인에게 배정되지 않은 준비물의 완료 상태를 바꿀 수 없다. 거절된 요청은 완료 상태·상태 토큰·중복 요청 기록을 변경하지 않는다.

화면은 개인 담당자가 있는 항목만 표시한다. ‘이전 공용’ 필터·전환 안내·직접 편집 화면은 제공하지 않는다. 담당자 탈퇴 시 기존 FK에 의해 NULL 항목이 생길 수 있으므로 서버의 담당자 검증은 유지하며, 담당자가 없는 항목의 완료·취소는 `409 PACKING_ASSIGNMENT_REQUIRED`로 막는다. 오래된 공용 완료 요청의 캐시 응답도 담당자 검증을 우회하지 않는다.

## 동시 수정과 재시도

`stateToken`은 항목 ID·여행 ID·이름·DB 담당 멤버 ID·완료 여부로 계산한 해시다. 별도 DB 컬럼으로 저장하지 않는다. 서버는 사용자 → 여행 → 준비물 잠금 순서를 지키고 현재 토큰과 요청의 `expectedStateToken`을 비교한다.

다르면 `409 PACKING_ITEM_CONFLICT`로 거절한다. 프론트엔드는 최신 목록을 반영하면서 편집 중인 이름·담당자 초안을 보존한다. 최신 토큰으로 자동 저장하지 않고 사용자가 내용을 확인한 뒤 다시 저장하도록 한다. 다른 멤버가 삭제한 항목은 재생성하지 않고 삭제 안내와 입력 초안을 유지한다.

목록은 ID 오름차순 커서로 조회하며 `limit`은 1~100이다. 목록 전체의 `checklistStateToken`을 커서에 포함해 페이지 사이에 변경이 생기면 `409 PACKING_LIST_CHANGED`로 알린다. 프론트엔드는 최대 3번 목록을 처음부터 다시 조회하고, 완전한 목록을 받았을 때만 화면 데이터를 교체한다. 실패하면 기존 목록을 유지한다.

요청 재시도는 기존 `api_idempotency`의 24시간 보관 기능을 사용한다.

- 인증·현재 여행 접근 확인 후 저장된 응답을 먼저 확인한다. 성공한 요청은 항목 삭제나 여행 보관 이후에도 같은 키·입력으로 재확인할 수 있다.
- 완료 요청은 중복 응답을 확인하기 전에 현재 담당자 권한도 검사한다. 담당자가 바뀌면 이전 담당자의 새 요청과 이전 완료 요청의 재시도를 모두 거절한다. 기존 완료 상태는 유지하며 새 담당자가 취소할 수 있다.
- 같은 키와 다른 입력은 `409 IDEMPOTENCY_KEY_REUSED`다.
- 배포 전 저장된 개인 단건 생성 응답은 재시도 시 `{ items: [기존 항목] }`로 감싸 호환한다. 담당자 없는 옛 공용 생성 응답은 `409 PACKING_ASSIGNMENT_REQUIRED`로 거절하며 새 전체 등록으로 재적용하지 않는다. 프론트엔드도 생성 응답의 모든 항목에 개인 담당자가 있는지 검증한다.
- 응답 유실 시 원래 입력·예상 토큰·키를 보존하고 명시적 재시도 버튼으로 같은 요청을 보낸다.
- 서버 저장 성공을 확인한 뒤 목록 조회만 실패한 경우에는 재시도 시 조회만 수행한다.
- 확인되지 않은 요청이 24시간을 넘으면 자동 재전송하지 않는다. 최신 목록 조회에 성공한 뒤 만료 요청을 폐기하고 `PACKING_RETRY_EXPIRED` 안내를 전달한다. 편집 화면은 초안을 유지하면서 저장을 잠그고 목록 확인 버튼을 제공한다. 목록에서 등록 여부를 확인한 뒤 새 화면에서 새 요청을 만들 수 있다.

토큰은 현재 값의 차이를 검출한다. 변경 후 원래 값으로 완전히 돌아온 이력은 감지하지 않는다. 재시도 식별자는 현재 로그인 세션의 메모리에 보관되므로 앱을 재시작해 저장 결과가 불확실하면 최신 목록을 먼저 확인해야 한다.

## 프론트엔드

- 신규 등록은 기존 `SelectField` 콤보박스에서 ‘모든 멤버가 각자 준비’ 또는 개인 담당자를 선택한다. 현재 몇 명에게 생성되는지 안내한다. 수정 화면은 개인 담당자만 선택한다.
- 목록은 담당자와 준비 완료·미완료 상태를 명시하며 멤버별 완료 수와 남은 수를 표시한다. 담당자별 필터로 다른 멤버의 상태를 확인할 수 있다.
- 완료 상태는 목록의 체크박스로만 변경한다. Mock 모드에서도 내용 수정은 기존 완료 상태를 보존한다.
- 다른 사람에게 배정된 준비물의 체크박스는 비활성화하고 담당자만 변경할 수 있다는 접근성 안내를 제공한다. 완료 상태와 담당자는 계속 조회할 수 있다.
- HTTP 저장소와 Mock 명령에도 담당자 권한 검증을 적용한다. 응답 유실이나 조회 실패로 보류된 완료 요청도 현재 담당자를 다시 확인한다. 서버에서 담당자 변경에 따른 403을 받으면 최신 목록을 반영한다.
- 저장 중·보관 여행의 추가/수정/체크/삭제를 비활성화한다.
- 탭 진입·앱 복귀·당겨 새로고침·변경 성공 시 서버 데이터를 조회한다. 다른 기기의 변경은 이 갱신 시점에 반영되며 실시간 푸시 동기화는 아니다.
- 홈과 여행 개요도 개인 항목으로 완료·미완료 수를 집계하고 이전 공용 기록은 제외한다. 준비물 0개와 모두 완료한 상태를 구분한다.
- 공유 안내에서 준비물을 서버 공유 항목으로 옮기고 공지·대화의 기기 저장 안내는 유지한다.

기기 데이터 전환:

1. 기존 API 주소·계정별 저장 원본에 준비물이 있으면 `:checklist-backup-v1` 키에 원본 전체를 복사한다. 이미 있는 백업은 덮어쓰지 않는다.
2. HTTP 모드의 `trip.checklist`는 서버 조회 결과로 채운다. 기기 목록을 섞거나 자동 업로드하지 않는다.
3. `localCollections`에서 준비물을 제외한다. 공지·대화 저장 후에도 별도 준비물 백업과 보존 안내는 유지한다.
4. Mock 모드의 로컬 준비물 저장은 유지한다.

## 실행과 검증
