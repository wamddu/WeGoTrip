# 여행 공지 서버 공유·푸시 변경안

상태: 2026-10-25 사용자가 “trip_notice 추가 승인”으로 승인한 후 `015-trip-notices.sql`을 WeGoTrip DB에 적용 완료했다. 기존 테이블 구조·건수는 유지했고 새 공지나 과거 데이터의 푸시 대기는 생성하지 않았다. 적용 전 스키마는 `tmp/chat-diagnostics/schema-before-015-1792916371825.sql`에 보관했다.

## 기능

- 여행장(방장)만 공지 작성·수정·삭제·고정을 수행한다. 현재 여행 멤버는 목록과 내용을 조회한다. 서버에서 권한을 검사한다.
- 공지는 제목(100자), 본문(3,000자), 고정 여부를 저장한다. 고정 우선·최신순으로 표시한다. 보관된 여행은 조회만 허용한다.
- 새 공지를 만들 때 작성자를 제외한 현재 여행 멤버의 등록 기기로 푸시를 예약한다. 계정별 푸시 설정을 존중하며 발송 직전 멤버십·기기·설정을 재검사한다.
- 공지 수정·고정 변경·삭제는 추가 푸시를 만들지 않는다. 삭제된 공지의 미발송 작업은 건너뛴다.
- 잠금 화면에는 공지 원문 대신 기본 안내를 표시한다. 알림을 누르면 수신 계정과 로그인 상태를 확인한 뒤 해당 여행 공지 화면으로 이동한다.
- 기존 기기에만 저장된 공지는 서버에 자동 업로드하지 않고 원본 저장소에 보존한다. 서버 공지 목록과 섞지 않는다.

## 승인 요청 DB 변경

`015-trip-notices.sql`로 신규 테이블 `trip_notice` 하나를 추가했다. 적용 전 읽기 전용 재확인에서 WeGoTrip 전체 테이블의 225개 컬럼과 외래키를 조회했다. 기존 `notification`은 `id, user_id, title, content, type, is_read`로 구성된 개인 알림 테이블이며 여행 연결·고정·작성 시각·수정 버전이 없다. `trip_member.notification_enabled`, `user_setting`, `user_device`, `push_event`, `push_delivery`는 이미 존재하므로 수신 정책과 발송에 재사용한다. 적용 전에는 여행 공지 원문을 여행과 연결해 저장하는 테이블이 없었다.

| 컬럼 | 용도 |
| --- | --- |
| id, trip_id | 공지 ID 및 여행 연결, 여행 삭제 시 함께 정리 |
| author_id | 작성자 연결, 계정 삭제 시 NULL로 보존 |
| title, body, pinned | 제목·본문·고정 여부 |
| version | 오래된 편집 화면에서 다른 변경을 덮어쓰지 않도록 충돌 검사 |
| created_at, updated_at | 생성·수정 시각 |

여행·공지 목록 인덱스 `(trip_id, id)`를 추가한다. 기존 회원·여행·채팅·푸시 테이블은 변경하지 않는다. 기존 `push_event`·`push_delivery`에 `TRIP_NOTICE` 종류를 사용하므로 푸시 스키마 추가 변경은 없다. 새 공지와 발송 대상 스냅샷은 같은 트랜잭션에 저장하고, 기기별 발송은 커밋 후 기존 공통 작업자가 처리한다.

적용 전에 관련 스키마를 백업하고 생성 후 컬럼·외래키·인덱스를 확인한다. 과거 채팅이나 기기 공지는 소급 발송하지 않는다. 자동화 검증에는 격리된 H2와 모의 FCM만 사용하며 별도 실기기 테스트 알림은 보내지 않는다.
