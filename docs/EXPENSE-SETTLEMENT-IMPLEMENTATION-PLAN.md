# 지출 기록 및 정산 기능 구현 계획

작성 기준: 2026-10-02 실제 MySQL 구조와 현재 프론트엔드·백엔드 코드.

**후속 상태: 구현 완료.** 2026-10-02 사용자가 제안한 DB 변경을 명시적으로 승인했다. 마이그레이션 009를 실제 DB에 적용하고 API·프론트엔드를 연결했다. 최종 변경과 검증 결과는 [구현 정리](EXPENSE-SETTLEMENT-IMPLEMENTATION.md)를 참조한다.

아래 본문은 승인 전 조사·계획을 보존한 원문이다. 원문의 “미승인”, “변경하지 않았다”는 계획 작성 당시의 상태다.

사용자는 지출의 소그룹·메모·송금 완료 상태도 서버에서 공유하기를 선택했다. 이 선택은 **DB 변경 승인으로 간주하지 않는다.** 필요한 변경은 [별도 DB 검토안](EXPENSE-SETTLEMENT-DB-PROPOSAL.md)에 정리했으며, 승인 전에는 적용하지 않는다.

## 1. 구현 방향

현재 화면과 입력 폼을 재사용하고, 기기에만 저장하던 지출과 정산 완료 표시를 서버에 연결한다. 정산 계산도 서버에서 수행해 모든 멤버가 같은 결과를 조회하게 한다.

| 기능 | 현재 DB만으로 가능 여부 | 계획 |
| --- | --- | --- |
| 지출 제목·금액·날짜·결제자 저장 | 가능 | 기존 `expense` 사용 |
| 개인별 분담금 저장 | 가능 | 기존 `expense_participant` 사용 |
| 멤버별 결제액·부담액·정산 경로 계산 | 가능 | 저장된 전체 지출로 서버에서 계산 |
| 지출의 소그룹 연결·메모 공유 | 불가능 | 두 컬럼 추가안 별도 검토 |
| 송금 완료·취소 상태 공유 | 불가능 | 완료 상태 테이블과 정산 버전 추가안 별도 검토 |

사용자가 서버 공유를 선택했으므로, 부족한 항목을 기기 저장으로 대체하는 구현은 진행하지 않는다. 전체 구현은 DB 변경안 승인 후 착수한다.

## 2. 실제 DB 조사 결과

`SHOW CREATE TABLE`, `information_schema`, 행 수·분담금 합계 조회로 확인했다. DB 접속 정보나 개인 데이터는 문서에 포함하지 않는다.

### expense

| 컬럼 | 타입·제약 | 의미 |
| --- | --- | --- |
| `id` | BIGINT, PK, AUTO_INCREMENT | 지출 ID |
| `trip_id` | BIGINT, NOT NULL, FK | 소속 여행 |
| `payer_trip_member_id` | BIGINT, NOT NULL, FK | 결제자의 여행 멤버 ID |
| `title` | VARCHAR(150), NOT NULL | 지출 제목 |
| `amount` | DECIMAL(15,2), NOT NULL | 지출 금액 |
| `expense_date` | DATE, NOT NULL | 지출 날짜 |

여행 삭제는 CASCADE, 결제자 멤버 삭제는 RESTRICT다. 소그룹·메모·작성자·생성/수정 시각·버전·통화 컬럼은 없다.

### expense_participant

| 컬럼 | 타입·제약 | 의미 |
| --- | --- | --- |
| `id` | BIGINT, PK, AUTO_INCREMENT | 분담 기록 ID |
| `expense_id` | BIGINT, NOT NULL, FK | 지출 ID |
| `trip_member_id` | BIGINT, NOT NULL, FK | 분담자의 여행 멤버 ID |
| `amount` | DECIMAL(15,2), NOT NULL | 해당 멤버의 분담금 |

`(expense_id, trip_member_id)`는 UNIQUE다. 지출 삭제와 멤버 삭제 모두 CASCADE다. **분담자 멤버를 삭제하면 과거 분담금까지 사라질 수 있으므로**, 회원 탈퇴 경로를 함께 보호해야 한다.

### 함께 확인한 내용

- 조회 당시 두 지출 테이블은 각각 **0행**이었다. 기기에 저장된 기존 지출이 없다는 뜻은 아니다.
- 실제 DB에는 정산·송금 완료 상태를 저장할 테이블이 없다. 기존 문서의 표현보다 현재 DB 조회 결과를 기준으로 한다.
- `trip_member.id`와 `user.id`는 서로 다른 ID다. 현재 화면은 사용자 ID를 사용하므로 서버에서 여행 멤버 ID로 변환한다.
- `trip_budget`에는 금액·통화가 있지만, 현재 여행 API의 예산은 `trip.budget`을 사용한다. 이번 작업에서 예산 저장 경로를 바꾸거나 이중 저장하지 않는다.
- DB는 소수 금액을 담을 수 있지만, 현재 UI는 원화 정수만 받는다. 이번 구현도 원화 정수 기준이다.

## 3. 유지할 기능과 입력 규칙

| 항목 | 규칙 |
| --- | --- |
| 제목 | 공백만 있는 입력 불가, 최대 150자. 현재 도메인의 100자 제한을 DB·폼과 일치시킴 |
| 금액 | 1~1,000,000,000원, 정수. 음수·0원·소수·문자열 숫자 입력 거절 |
| 날짜 | 유효한 `YYYY-MM-DD`. 예약·준비 비용을 위해 여행 기간 밖 날짜도 허용 |
| 결제자 | 해당 여행의 멤버. 분담자 목록에 포함될 필요는 없음 |
| 분담자 | 1명 이상, 중복 불가, 모두 해당 여행의 멤버 |
| 분담금 | 0원 이상 정수, 합계가 지출 금액과 정확히 같아야 함 |
| 소그룹 | 선택 사항. 같은 여행의 소그룹만 연결 가능 |
| 메모 | 선택 사항, 최대 1,000자 |

균등 분담은 몫을 나누고 남은 원을 선택된 멤버의 고정 순서대로 1원씩 배정한다. 예를 들어 **2원을 3명에게 나누면 1원·1원·0원**이며, 0원 분담자도 선택 기록으로 저장한다. 직접 지정은 입력한 분담금을 그대로 저장한다. 별도의 분담 방식 컬럼은 필요하지 않다.

소그룹 선택은 분담자 초기 선택과 지출 목록 분류에 사용한다. 사용자가 분담자를 직접 바꿀 수 있고, 소그룹 멤버가 나중에 바뀌어도 기존 지출의 분담금은 자동 변경하지 않는다. 정산 결과는 현재 UI처럼 **여행 전체**를 기준으로 계산한다. 소그룹 필터는 지출 목록만 제한한다.

## 4. API 제안

기존 Bearer JWT, `{ code, data }` 성공 응답과 `{ code, message }` 오류 응답을 사용한다. ID와 버전은 문자열로 전송하고 BIGINT를 JavaScript Number로 변환하지 않는다. 아래 계약은 구현 시 확정할 제안이다.

| 메서드 | 경로 | 성공 | 기능 |
| --- | --- | --- | --- |
| GET | `/api/v1/trips/{tripId}/expenses` | 200 | 지출 목록과 현재 정산 버전 |
| GET | `/api/v1/trips/{tripId}/expenses/{expenseId}` | 200 | 지출 단건과 현재 정산 버전 |
| POST | `/api/v1/trips/{tripId}/expenses` | 201 | 지출·분담금 동시 등록 |
| PUT | `/api/v1/trips/{tripId}/expenses/{expenseId}` | 200 | 지출·분담금 전체 수정 |
| DELETE | `/api/v1/trips/{tripId}/expenses/{expenseId}` | 200 | 지출 삭제 |
| GET | `/api/v1/trips/{tripId}/settlement` | 200 | 전체 정산 결과·완료 상태 |
| PUT | `/api/v1/trips/{tripId}/settlement/confirmations` | 200 | 특정 송금의 완료·취소 기록 |

지출 등록 입력 예시:

```json
{
  "title": "저녁 식사",
  "amount": 30000,
  "date": "2026-10-02",
  "payerId": "101",
  "shares": { "101": 10000, "102": 10000, "103": 10000 },
  "partyId": "7",
  "note": "식사와 음료 포함"
}
```

`payerId`와 `shares`의 키는 **사용자 ID**다. DB 저장 시 해당 여행의 `trip_member.id`로 변환하고, 응답에서는 다시 사용자 ID로 돌려준다.

- 등록·수정·삭제·완료 기록의 모든 논리 요청은 UUID `Idempotency-Key`를 사용한다. 네트워크 재시도에는 같은 키와 입력을 유지한다.
- 수정·삭제 입력에는 화면을 읽었을 때의 `settlementRevision`을 포함한다. 다른 멤버가 먼저 지출을 바꿨다면 409로 거절하고 최신 내용을 다시 확인하게 한다.
- 수정은 body, 삭제는 `?settlementRevision=...` query로 기대 버전을 전달한다. 새 지출 등록은 기존 지출을 덮어쓰지 않으므로 기대 버전을 필수로 받지 않고, 잠근 현재 버전에서 증가시킨다.
- 완료 기록 입력은 `{ settlementRevision, fromUserId, toUserId, amount, completed, confirmationVersion }`이다. 토글 명령 대신 `completed: true/false`라는 목표 상태를 전송한다.
- 완료 여부가 없는 송금은 `completed=false`, `confirmationVersion="0"`으로 반환한다. 상세 버전·중복 요청 규칙은 별도 DB 검토안에 정리했다.
- 목록은 ID 오름차순 cursor와 limit 1~100을 사용한다. cursor에는 정산 버전도 포함하고, 페이지 사이 지출이 바뀌면 처음부터 재조회한다.
- 프론트엔드는 모든 페이지를 조회한다. 정산 API는 페이지나 소그룹 필터와 관계없이 전체 지출을 계산한다.
- 지출 목록과 정산 응답의 버전이 다르면 일치할 때까지 제한적으로 재조회하고, 계속 바뀌면 재시도 안내를 표시한다. 서로 다른 기준의 목록·정산을 함께 표시하지 않는다.
- 응답은 `Cache-Control: no-store`를 적용한다.

## 5. 서버 정산 계산

멤버별로 다음 값을 계산한다.

```text
결제액 = 해당 멤버가 결제한 모든 지출의 합
부담액 = 해당 멤버에게 배정된 모든 분담금의 합
잔액   = 결제액 - 부담액
```

잔액이 양수면 받을 사람, 음수면 보낼 사람이다. 멤버 목록과 같은 `joined_at, id` 순서를 고정하고, 보낼 사람과 받을 사람을 순서대로 연결해 작은 쪽 금액을 배정한다. 현재 프론트엔드 계산 방식과 맞춘다. 이 방식은 전체 잔액을 맞추지만, 가능한 모든 경우에서 송금 횟수가 최소라고 보장하지는 않는다.

예를 들어 A가 30,000원을 결제하고 A·B·C가 각각 10,000원을 부담했다면:

| 멤버 | 결제액 | 부담액 | 잔액 | 정산 |
| --- | ---: | ---: | ---: | --- |
| A | 30,000 | 10,000 | +20,000 | B·C에게 각각 10,000원 받음 |
| B | 0 | 10,000 | -10,000 | A에게 10,000원 보냄 |
| C | 0 | 10,000 | -10,000 | A에게 10,000원 보냄 |

서버는 BigDecimal 기반의 정확한 원 단위 계산을 사용한다. 지출마다 분담금 합계를 검사하고 전체 잔액 합계가 0인지 확인한다. 기존 DB에 소수 금액·누락 분담·합계 불일치가 발견되면 임의 반올림·보정하지 않는다. 숫자로 반환하는 금액은 JavaScript 안전한 정수 범위를 확인하고, 초과 시 오류로 처리한다.

정산 응답에는 `settlementRevision`, 총 지출, 멤버별 `paid/share/balance`, 송금별 `from/to/amount/key/completed/confirmationVersion`을 포함한다. 송금 key에도 정산 버전을 포함해 이전 계산의 버튼과 현재 계산을 구분한다.

## 6. 권한·보관·데이터 보존

- 조회와 지출 등록·수정·삭제는 현재 여행 멤버만 할 수 있다. 현재 화면의 공동 편집 동작을 유지하며, 없는 작성자 컬럼을 이용한 권한 구분은 추가하지 않는다.
- 보관한 여행은 지출 조회와 정산 조회가 가능하지만 지출 변경은 금지한다. 다시 열면 변경할 수 있다.
- 송금 완료·취소는 해당 송금의 보내는 사람 또는 받는 사람만 가능하다. 현재 UI와 같이 보관한 여행에서도 가능하다.
- 여행장이라는 이유만으로 다른 두 멤버 사이의 완료 표시를 변경할 수는 없다.
- 다른 여행의 지출·결제자·분담자·소그룹을 입력하면 거절한다. 지출 ID만으로 수정하거나 멤버 ID를 그대로 신뢰하지 않는다.
- 지출이 연결된 소그룹 삭제도 409로 막는다. 현재 백엔드의 일정 참조 검사에 지출 참조 검사를 추가해 프론트엔드와 맞춘다.
- 지출의 결제자·분담자 또는 정산 완료 기록에 참조된 멤버는 물리 삭제를 막는다. 회원 탈퇴 과정도 참조 검사 전에 멤버를 삭제하지 않게 한다.

마지막 규칙은 **정산을 마쳤더라도 기록에 참조되면 현재 방식의 회원 탈퇴가 제한되는 정책 제안**이다. 계정을 탈퇴하면서 과거 기록을 유지하려면 멤버 보존·사용자 익명화 등의 별도 설계가 필요하며, 이번 최소 DB 변경안에 몰래 포함하지 않는다.

## 7. 송금 완료 표시의 의미

완료 표시는 현재 화면처럼 실제 송금 후 당사자가 직접 남기는 확인 표시다. 은행 송금, 부분 송금 금액, 실제 송금액을 잔액에서 차감하는 누적 원장은 구현 범위에 포함하지 않는다.

성공한 지출 등록·수정·삭제마다 정산 버전을 증가시키고, 새 버전의 완료 표시는 모두 대기로 시작한다. **메모·소그룹만 수정하거나 같은 내용을 다시 저장한 경우도 현재 UI 규칙대로 초기화한다.** 같은 요청의 재시도나 실패한 저장은 버전을 증가시키지 않는다. 여행 이름·예산·소그룹 멤버 변경만으로는 초기화하지 않는다.

예를 들어 B→A 10,000원 송금을 완료로 표시한 뒤 새 지출이 생기면 새 정산 결과를 다시 표시한다. 과거 실제 송금 10,000원을 자동 차감한 잔액을 보여주는 기능은 아니다. 그런 누적 정산이 필요하면 송금 원장과 계산 정책을 추가로 설계해야 한다.

이전 버전의 완료 기록은 보존하되 현재 화면에는 적용하지 않는다. 지출을 수정했다가 원래 값으로 되돌려도 예전 완료 표시가 다시 살아나지 않는다. 보존되는 것은 버전별 마지막 완료 상태이며, 당시 지출 원본이나 모든 체크 변경의 감사 기록은 아니다.

| 파일·영역 | 예정 작업 |
| --- | --- |
| `frontend/src/data/trip-api.ts` | 지출 CRUD·정산 조회·완료 기록 계약, 전체 페이지 조회, ID·금액 검증 |
| `frontend/src/data/user-travel-repository.ts` | 실제 HTTP 모드에 서버 조회·저장 연결. 지출·완료 상태를 기기 배열로 덮어쓰지 않음 |
| `frontend/src/domain/models.ts` | 서버 정산 결과와 버전·완료 버전 모델 추가. mock 계산 방식은 호환 유지 |
| `frontend/src/domain/commands.ts` | 제목·메모 제한 통일, 완료 목표 상태·버전 전달, 기존 mock 검증 유지 |
| `frontend/src/features/trip/edit-screen.tsx` | 기존 지출 폼을 서버 저장에 연결. 충돌·저장 실패 시 작성 내용 유지 |
| `frontend/src/features/trip/expense-section.tsx` | 실제 HTTP 모드에서는 서버 정산 응답을 표시. 현재 레이아웃·소그룹 필터 유지 |
| `frontend/src/features/trip/trip-screen.tsx` | 기기 저장 안내에서 정산을 제외하는 최소 문구 수정 |

송금 버튼은 클릭 당시 목표 상태와 버전을 고정한다. 실패하면 오류를 표시하고 기존 확인 상태를 유지한다. 성공 후 화면 재조회가 실패해도 같은 요청을 다시 토글하지 않는다. 409는 최신 상태를 조회해 사용자가 다시 판단하게 하고, 자동으로 오래된 선택을 덮어쓰지 않는다.

기존 기기 지출은 즉시 업로드하거나 서버 데이터와 합치지 않는다. 원본을 별도 보존하고 서버 공유로 전환되었음을 알린다. 기존 자료의 명시적 내보내기·가져오기는 중복 방지와 로컬 ID 변환을 갖춘 후속 기능으로 분리한다. 서버 조회 실패를 지출 0건으로 표시하지 않는다.

## 9. 백엔드 연결 위치와 트랜잭션

기존 JDBC 서비스 구조에 `ExpenseController/ExpenseService`, `SettlementController/SettlementService`를 추가하는 방식으로 계획한다. 새 Controller를 `UserApiErrors` 처리 대상에 포함한다.

인증 사용자 → 여행 → 지출·분담·완료 기록 순서로 잠근다. 등록·수정에서 지출과 분담금 교체, 정산 버전 증가, 중복 요청 결과 저장을 하나의 트랜잭션으로 묶는다. 분담금 저장이 실패하면 지출과 버전도 함께 롤백한다.

기존 `api_idempotency`를 재사용하지만 현재 `PlanningSupport.remember()`는 생성 응답 201에 맞춰져 있다. 수정·삭제·완료 응답의 200을 보존하도록 일반화한다. 목록 helper의 테이블 허용 목록·ID cursor도 지출과 정산 버전에 맞춰 확장하거나 별도 구현한다.

중복 응답을 돌려줄 때도 현재 계정과 여행 접근 권한을 확인한다. 임시 중복 요청 테이블을 영구 지출·송금 상태 저장소로 이용하지 않는다. 같은 여행을 잠그는 회원 탈퇴와 경합해도 분담금이 사라지지 않게 한다.

## 10. 구현 순서와 검증

1. **별도 DB 검토안 승인**: 소그룹·메모·정산 버전·완료 테이블과 기록 보존 정책을 확인한다.
2. **마이그레이션 준비**: 실제 적용 직전에 메타데이터·행 수·분담금 합계를 재확인하고 백업·복구 방안을 마련한다. 테스트 DB에서 검증한 후 승인된 변경만 적용한다.
3. **백엔드 구현**: 지출 CRUD → 정확한 정산 계산 → 버전·완료 공유 → 참조 삭제 보호 순서로 구현한다.
4. **프론트엔드 연결**: HTTP 모드의 기기 저장을 서버 저장으로 전환하고 기존 폼·목록·정산 화면을 연결한다.
5. **통합 검증**: 두 멤버·두 기기에서 동일한 지출·정산·완료 상태를 확인한다.

| 검증 범위 | 대표 사례 |
| --- | --- |
| 금액·분담 | 2원/3명, 직접 지정, 0원 분담자, 합계 불일치, 소수·음수·과도한 금액 |
| 권한·참조 | 다른 여행 ID 입력, 비멤버 접근, 결제자는 분담자에서 제외, 소그룹 삭제 제한 |
| 트랜잭션 | 분담금 저장 실패 시 전체 롤백, 동일 요청 재시도 시 중복·버전 증가 없음 |
| 정산 | 전체 잔액 0, 안정된 송금 순서, 소그룹 필터가 전체 계산에 영향을 주지 않음 |
| 완료 공유 | 당사자만 완료·취소, 보관 여행 완료 허용, 두 기기 동시 변경 충돌 |
| 재정산 | 메모만 수정·같은 내용 저장 시 초기화, A→B→A 수정 시 과거 완료 부활 없음 |
| 동시성 | 지출 수정과 완료 경합, 응답 유실 후 재시도, 오래된 버전의 완료·취소 거절 |
| 조회 | 여러 페이지 전체 반영, 조회 중 변경 시 재시작, API 실패를 빈 목록으로 표시하지 않음 |
| 기록 보존 | 분담자만 있는 계정·0원 분담자·보관 여행 멤버의 탈퇴 시 기록 보존 |
| 전환 | 기기 원본 보존, 자동 업로드 없음, HTTP와 mock 경로 모두 확인 |

H2 테스트만으로 MySQL 외래키·CASCADE·잠금 동작을 확인했다고 판단하지 않는다. 관련 경합과 삭제 순서는 실제 MySQL을 사용하는 분리된 테스트 환경에서도 확인한다. 현재 작업은 문서 작성 단계이므로 이 구현 테스트들은 아직 실행하지 않았다.

## 11. 다음 결정

DB 변경안과 정책을 먼저 검토한다. 승인 이후에 마이그레이션과 API·프론트엔드 연결을 진행할 수 있다. 현재 서버 구조에서 영구 저장할 수 없는 필드를 숨기거나 기기에만 남기는 대안으로 임의 구현하지 않는다.
