# 여행 공지 구현

## 적용 상태

2026-10-25 서버·클라이언트 구현 및 사용자 승인 후 실제 WeGoTrip DB의 `trip_notice` 테이블 추가를 완료했다. `015-trip-notices.sql`의 컬럼·인덱스·외래키를 확인했고 기존 테이블 구조·건수는 유지했다. 적용 전 스키마는 `tmp/chat-diagnostics/schema-before-015-1792916371825.sql`에 보관했다. 기존 `notification`은 개인 알림 저장용이며 변경하지 않았다. 변경 근거와 범위는 [DB 변경안](TRIP-NOTICE-PROPOSAL.md)에 있다.

현재 연결된 DB에는 015 적용이 완료됐으므로 백엔드를 다시 실행하고 클라이언트를 새로고침하면 새 기능을 사용할 수 있다. 다른 배포 DB에는 014까지 준비한 뒤 015를 적용해야 한다. 서버·클라이언트 프로세스는 자동으로 시작하지 않았다.

## 사용자 동작

- 현재 여행장만 공지 작성·수정·삭제·고정을 수행한다. 일반 멤버는 공지 목록과 본문을 볼 수 있다. 클라이언트 화면과 서버 API 모두 권한을 검사한다.
- 제목 100자·본문 3,000자이며 고정 공지를 우선하고 최신순으로 표시한다. 여러 공지를 고정할 수 있다. 개요와 실제 서버 채팅에서도 고정 공지를 열 수 있다.
- 목록 진입, 앱 복귀, 새로고침 때 서버 공지를 다시 불러온다. 공지 전용 실시간 소켓은 추가하지 않았다.
- 알림을 누르면 현재 로그인 계정을 확인하고 여행 공지 화면으로 이동하며 해당 공지를 먼저 보여 준다. 삭제된 공지라면 목록과 삭제 안내를 표시한다.
- 보관된 여행은 조회만 허용한다. 오래된 편집 화면의 저장·삭제는 `NOTICE_CONFLICT`로 거절한다. 입력은 유지하고 사용자가 최신 공지를 다시 불러온 뒤 수정한다.
- 기존 기기 공지는 원본 저장소에 보존하며 서버로 자동 업로드하거나 공유 공지 목록에 섞지 않는다. 남아 있는 원본이 있으면 화면에 보관 안내를 표시한다.

## API

인증된 `/api/v1/trips/{tripId}/notices` 아래에 제공한다. 비멤버는 404, 멤버의 관리 요청은 403이다.

| 요청 | 설명 |
| --- | --- |
| GET / | 목록, `limit` 1~100, 여행에 종속된 `cursor` |
| GET /{noticeId} | 공지 조회 |
| POST / | 여행장 작성, `{title, body, pinned}` |
| PUT /{noticeId} | 여행장 수정, `{title, body, pinned, expectedVersion}` |
| DELETE /{noticeId}?expectedVersion=... | 여행장 삭제 |

생성·수정·삭제는 UUID `Idempotency-Key`를 요구한다. 응답의 ID와 `version`은 정밀도를 보존한 문자열이다. 작성자·생성 시각은 서버가 확정하며 수정 시 원래 작성자를 보존한다. 클라이언트는 불확실한 저장 결과에 같은 입력·버전·키를 유지한다. 저장 후 목록 갱신만 실패하면 쓰기를 반복하지 않고 갱신만 재시도한다. 24시간이 지난 불확실한 요청은 다시 발송하지 않고 목록 확인을 요청한다.

## 푸시

새 공지 생성 시 기존 `push_event`·`push_delivery`를 `TRIP_NOTICE` 종류로 재사용한다. 원문 저장과 대상 스냅샷은 같은 트랜잭션이며 기기별 발송 준비는 커밋 후 실행한다. 새 공지와 푸시 대상 기록은 함께 성공하거나 취소된다. 수정·고정 변경·삭제에는 추가 푸시를 보내지 않는다.

작성자 자신의 기기를 제외한 현재 멤버 중 계정 푸시 및 기존 `trip_member.notification_enabled`가 허용된 계정의 기기만 대상으로 삼는다. 발송 직전에 멤버십·계정 상태·설정·토큰·공지 존재와 여행 활성 상태를 다시 확인한다. 탈퇴, 여행 보관, 토큰 변경 또는 공지 삭제 시 대기를 건너뛴다. 재시도·임대·FCM 등록 해제 기기 정리는 기존 공통 작업자를 사용한다.

알림은 `새 여행 공지` / `참여 중인 여행에 새 공지가 등록됐어요.`이며 원문·작성자 이름을 FCM에 싣지 않는다. 데이터는 종류·수신자·여행·공지·이벤트·발송 ID다. 네이티브 foreground 로컬 알림, 백그라운드/종료 후 열기, 웹 foreground·서비스 워커 클릭 처리를 확장했다. 앱 내 개인 알림함(`notification`) CRUD는 이번 범위에 포함하지 않는다.

기존 `PUSH_ENABLED`, Firebase 서버 인증, 등록 기기, OS 권한 및 계정 푸시 설정이 필요하다. 설정은 [푸시 실행 안내](CHAT-PUSH-IMPLEMENTATION.md)를 참고한다. 이전 사용자 요청에 따라 실제 기기에 테스트 알림을 발송하지 않았다.

## 검증

백엔드 전체 148개 테스트와 프런트엔드 169개 테스트가 통과했다. TypeScript 검사와 웹·Android·iOS 번들 생성도 통과했다. 실제 DB 적용 후 회원 19건·여행 7건·채팅 10건 및 개인 알림·푸시 이벤트·발송 건수가 모두 유지됨을 확인했다. 신규 공지는 0건이며 적용 과정에서 알림을 발송하지 않았다. 실제 기기 수신 검증은 사용자의 이전 요청에 따라 수행하지 않았다.

`NoticeApiTests`는 방장 권한·멤버 간 조회·위조 작성자 거절·중복 생성·공지/발송 원자성·수정 충돌·목록 페이지·보관된 여행·대상 제외·발송 직전 설정/멤버/토큰 변경·삭제 공지 발송 차단을 H2와 모의 FCM으로 검사한다. 프런트엔드는 서버 공유·이전 기기 원본 보존·권한·충돌·응답 유실 및 갱신 실패 재시도·키 만료·공지 API 계약·푸시 숫자 ID/URL 검증·서비스 워커 열기를 검사한다.
