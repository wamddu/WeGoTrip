# 지출·정산 서버 공유를 위한 DB 변경 검토안

작성 기준: 2026-10-02. [전체 구현 계획](EXPENSE-SETTLEMENT-IMPLEMENTATION-PLAN.md)에서 DB 변경 부분만 별도로 정리했다.

**후속 상태: 승인 및 실제 적용 완료.** 2026-10-02 사용자의 “제안한 DB 변경 승인” 답변에 따라 마이그레이션 009를 적용했다. 컬럼 3개와 테이블 1개를 추가했으며, 기존 지출·분담 컬럼과 외래키는 변경하지 않았다. [구현 정리](EXPENSE-SETTLEMENT-IMPLEMENTATION.md)에 적용·검증 결과를 기록했다.

본문의 설계는 최초 검토안이며, 아래 범위대로 승인받아 구현했다.

## 1. 제안 범위

| 대상 | 제안 변경 | 이유 |
| --- | --- | --- |
| 기존 `expense` | `party_id`, `note` 추가 | 지출의 소그룹·메모 공유 |
| 기존 `trip` | `settlement_revision` 추가 | 현재 정산 기준과 과거 완료 표시 구분 |
| 신규 `settlement_confirmation` | 송금별 완료 상태·버전·기록자 저장 | 기기·멤버 간 완료·취소 상태 공유 |

기존 `expense_participant`, 금액 컬럼, 예산 저장 구조, 기존 외래키는 변경하지 않는다. 제안은 **기존 테이블에 컬럼 3개 추가 + 신규 테이블 1개**다. 영구 저장이 필요하지만 현재 DB에서 표현할 수 없는 정보만 추가한다.

## 2. expense 추가 컬럼

| 컬럼 | 제안 타입·제약 | 기존 데이터 처리 |
| --- | --- | --- |
| `party_id` | BIGINT, NULL 허용, `trip_party(id)` FK, 인덱스 | NULL: 여행 공동 지출 |
| `note` | TEXT, NULL 허용 | NULL을 API에서 빈 문자열로 변환 |

`party_id` 외래키의 삭제 정책은 `ON DELETE SET NULL`을 제안한다. API에서는 일정 또는 지출에 연결된 소그룹의 삭제를 409로 막는다. DB의 SET NULL은 직접 DB 작업에서 참조가 끊어질 때를 위한 안전망이지, 연결된 소그룹의 API 삭제를 허용한다는 뜻이 아니다.

소그룹과 지출이 같은 여행에 속하는지는 서비스에서 검증한다. 단순 FK는 소그룹 ID의 존재만 검사하며 같은 여행까지 보장하지 않는다. 메모는 서버·프론트엔드에서 1,000자로 제한한다.

## 3. trip 추가 컬럼

| 컬럼 | 제안 타입·제약 | 기존 데이터 처리 |
| --- | --- | --- |
| `settlement_revision` | BIGINT, NOT NULL, DEFAULT 0 | 기존 여행은 0으로 시작 |

정산 버전은 성공한 지출 추가·수정·삭제마다 1 증가한다. 메모·소그룹 변경과 같은 내용 재저장도 포함한다. 동일 논리 요청의 재시도, 실패한 저장, 여행 이름·예산 변경, 소그룹 이름·멤버 변경만으로는 증가시키지 않는다.

기존 `trip.version`은 여행 설정의 동시 수정 검사에 계속 사용한다. 정산 버전으로 함께 쓰면 이름이나 예산 변경까지 송금 완료 표시를 초기화하므로 두 목적을 분리한다.

### 금액으로 만든 key나 해시만으로 부족한 이유

```text
정산 버전 10: A 상태, B→A 10,000원 완료
정산 버전 11: 지출을 수정해 B 상태로 변경
정산 버전 12: 다시 A 상태로 변경
```

A 상태로 돌아왔을 때 금액·멤버만 비교하면 버전 10의 완료 표시와 오래된 요청이 다시 유효해질 수 있다. 버전 12는 새로운 계산 기준이므로 **완료 대기**로 표시하고 버전 10 요청은 거절한다. 같은 금액을 저장해도 증가하는 번호가 필요하다.

## 4. settlement_confirmation 신규 테이블

| 컬럼 | 제안 타입·제약 | 의미 |
| --- | --- | --- |
| `id` | BIGINT, PK, AUTO_INCREMENT | 완료 기록 ID |
| `trip_id` | BIGINT, NOT NULL, FK | 소속 여행 |
| `settlement_revision` | BIGINT, NOT NULL | 완료 표시가 적용되는 정산 버전 |
| `from_trip_member_id` | BIGINT, NOT NULL, FK | 보낼 사람 |
| `to_trip_member_id` | BIGINT, NOT NULL, FK | 받을 사람 |
| `amount` | DECIMAL(18,2), NOT NULL | 해당 정산 제안 금액 |
| `completed` | TINYINT(1), NOT NULL, DEFAULT 0 | 완료 여부 |
| `version` | BIGINT, NOT NULL, DEFAULT 0 | 같은 정산 버전 안의 완료·취소 경합 검사 |
| `updated_by_trip_member_id` | BIGINT, NOT NULL, FK | 마지막으로 상태를 변경한 멤버 |
| `updated_at` | TIMESTAMP(6), NOT NULL, DEFAULT CURRENT_TIMESTAMP(6) | 마지막 실제 상태 변경 시각 |

제안 제약:

- UNIQUE: `(trip_id, settlement_revision, from_trip_member_id, to_trip_member_id)`.
- `trip_id → trip(id)`는 ON DELETE CASCADE.
- 보내는 사람·받는 사람·기록자 → `trip_member(id)`는 ON DELETE RESTRICT.
- 세 멤버 FK에 인덱스를 둔다. 여행·정산 버전 조회는 UNIQUE 인덱스의 앞부분을 사용한다.
- 세 멤버가 같은 여행에 속하는지, 기록자가 보내는 사람 또는 받는 사람인지 서비스에서 확인한다.
- 보내는 사람과 받는 사람은 달라야 하고 금액은 양수여야 한다. **현재 서버가 계산한 경로·금액과 일치하는 요청만** 저장한다.

제안한 계산 방식은 같은 정산 버전에서 동일한 두 사람 사이의 경로를 한 번만 만들기 때문에 위 UNIQUE 범위로 충분하다. 클라이언트가 임의로 만든 경로나 금액을 저장하지 않는다.

정산 금액은 여러 지출의 합일 수 있으므로 신규 테이블에서는 기존 지출의 DECIMAL(15,2)보다 큰 DECIMAL(18,2)를 제안한다. API의 안전한 정수 범위 검사를 통과한 원화 정수 금액을 담을 수 있다. 기존 지출·분담 금액 컬럼은 변경하지 않는다.

## 5. 조회·완료·취소 계약

현재 여행의 `settlement_revision`으로 전체 정산을 계산하고 해당 버전의 완료 기록만 결합한다. 모든 대기 송금에 테이블 행을 미리 만들 필요는 없다.

| 상황 | 처리 |
| --- | --- |
| 완료 행 없음 | `completed=false`, `confirmationVersion="0"` 반환 |
| 행 없이 완료 요청 | version 1인 완료 행 생성 |
| 기존 행의 완료·취소 상태가 실제로 변경됨 | 상태·기록자·시각 수정, version 1 증가 |
| 현재 버전·행 버전이 맞고 이미 같은 상태임 | 그대로 반환. version·시각 변경 없음 |
| 행 없이 취소 요청 | 대기 상태·version 0 반환. 불필요한 행 생성 없음 |
| 정산 버전이 다름 | 409 `SETTLEMENT_CHANGED` |
| 완료 행 버전이 다름 | 409 `CONFIRMATION_CHANGED` |

버전 검사는 이미 같은 상태인지 판단하기 **전**에 한다. 지출 버전은 오래된 정산 기준을 막고, 완료 행 버전은 같은 기준 안에서 두 당사자가 완료·취소를 번갈아 기록할 때 오래된 요청을 막는다.

예를 들어 완료(true, version 1) → 취소(false, version 2) 후 version 0이나 1에 기반한 새 완료 요청이 늦게 도착해도 취소를 덮어쓰지 않는다. 충돌하면 최신 상태를 조회해 사용자가 다시 판단한다.

## 6. 트랜잭션과 중복 요청

모든 지출 쓰기와 완료 PUT은 기존 `api_idempotency`와 UUID 요청 키를 재사용한다. 신규 중복 방지 테이블은 필요하지 않다.

digest에는 메서드·operation, 여행 ID, 지출 등 대상 ID, 기대 버전, 정규화한 입력을 포함한다. 분담자 입력 순서만 다른 동일 내용은 같은 형태로 정렬한다. 같은 키를 다른 지출이나 다른 작업에 사용해 엉뚱한 성공 응답을 재사용하지 않게 한다.

처리 순서는 다음과 같다.

1. 현재 계정 인증과 여행 접근 권한을 검사하고 사용자 → 여행 → 하위 행 순서로 잠근다. 완료 요청은 입력의 보내는 사람·받는 사람 중 인증 사용자가 있는지도 확인한다.
2. 요청 키와 정규화 입력 digest를 비교한다. 같은 성공 요청이면 추가 쓰기 없이 이전 응답을 반환한다. 다른 입력의 키 재사용은 409로 거절한다.
3. 새로운 요청은 요청 유형에 맞는 보관 여부·당사자 권한을 검사한다. 지출 수정·삭제와 완료 요청은 기대 정산 버전을 확인하고, 완료 요청은 현재 계산된 경로·금액과 완료 행 버전도 확인한다. 새 지출 등록은 기대 버전을 요구하지 않고 잠근 현재 정산 버전에서 처리한다.
4. 지출+분담금+정산 버전 또는 완료 행을 변경하고, 중복 요청 응답도 같은 트랜잭션에 저장한다.

보관 여행에서 새 지출 변경은 금지하고 완료·취소는 허용한다. 성공했던 지출 요청의 응답 재전송은 접근 권한을 다시 확인하되, 이후 보관되었다는 이유로 이미 끝난 쓰기를 다시 수행하거나 실패로 오인하지 않게 한다.

중복 응답에 포함된 옛 완료 상태를 현재 화면의 최종 상태로 강제 적용하지 않는다. 재시도 응답을 받은 뒤 최신 정산을 조회한다. 같은 완료 요청을 재실행하면 다른 당사자의 이후 취소를 덮어쓸 수 있으므로, 명시적 boolean과 중복 요청 보호를 함께 사용한다.

기존 중복 요청 보존 기간은 24시간이다. 이는 영구 중복 보장이 아니다. 기간이 지난 생성 요청을 자동 재전송하지 않고 최신 목록 확인을 안내한다. 업데이트·삭제·완료는 버전 검사도 함께 적용한다.

## 7. 과거 기록과 탈퇴 보호

지출 변경 뒤 이전 정산 버전의 완료 행은 지우지 않고 현재 조회에서 제외한다. 과거 행은 당시 송금 경로·금액과 마지막 체크 상태를 보존한다. **당시 지출 전체의 원본, 체크 변경 전부의 감사 기록, 실제 송금 원장까지 저장하는 구조는 아니다.**

기존 `expense_participant`의 멤버 삭제 CASCADE는 변경하지 않고 서비스에서 참조 멤버 삭제를 먼저 막는 안이다. 결제자뿐 아니라 분담자·완료 기록 참조 여부를 확인한다. 0원 분담자와 보관 여행도 검사한다.

이 정책은 현재 물리 삭제 방식의 **회원 탈퇴를 제한할 수 있다.** 잔액이 0이거나 송금을 마쳤다는 이유로 과거 참조를 삭제하면 기록이 깨지므로 허용하지 않는다. 탈퇴와 기록 보존을 모두 지원하는 익명화·멤버 보존 설계는 별도 검토가 필요하다.

현재 앱에는 여행 물리 삭제 기능이 없지만, 향후 추가한다면 CASCADE와 멤버 RESTRICT의 처리 순서를 실제 MySQL에서 검증해야 한다. 완료 기록 → 지출·분담금 → 멤버 → 여행 순으로 명시적으로 삭제하는 트랜잭션을 검토하고, 부모 삭제 한 번으로 안전하다고 가정하지 않는다.

## 8. 데이터 이행과 적용 절차

- 조회 당시 지출·분담 테이블은 0행이다. 적용 직전에 다시 검사한다.
- 기존 여행은 정산 버전 0, 기존 지출은 소그룹 NULL·메모 NULL로 유지한다. 새 완료 테이블은 빈 상태로 시작한다.
- 기기 지출과 완료 체크를 자동으로 서버에 올리지 않는다. 로컬 자료는 별도 보존하고 공유 기능으로 전환되었음을 안내한다.
- 현재 컬럼·FK의 실제 정의를 검사하는 마이그레이션을 작성하고, 일부 적용 상태와 재실행을 고려한다. 예상과 다른 정의는 자동으로 덮어쓰지 않는다.
- MySQL DDL은 애플리케이션 트랜잭션 롤백으로 전부 복구된다고 가정하지 않는다. 적용 전 백업, 테스트 적용, 변경별 검증 순서를 마련한다.
- 새 데이터가 생긴 뒤 컬럼·테이블을 단순 삭제하는 복구는 정보 손실을 일으킨다. 복구가 필요하면 공유 쓰기를 중지하고 새 데이터를 보존한 다음 진행한다.

## 9. 승인·검토 항목

| 구분 | 검토할 결정 |
| --- | --- |
| DB 변경 범위 | `expense.party_id`, `expense.note`, `trip.settlement_revision`, `settlement_confirmation` 1개 테이블 |
| 완료 의미 | 수동 확인 표시 공유. 실제 송금·부분 송금 원장·과거 송금액 자동 차감은 제외 |
| 재정산 정책 | 성공한 지출 저장·삭제마다 완료 표시 초기화. 이전 버전의 마지막 상태는 보존 |
| 삭제 정책 | 연결된 소그룹 삭제 거절, 참조된 멤버 물리 삭제·현재 방식의 회원 탈퇴 보호 |
| 기존 기기 자료 | 원본 보존, 자동 업로드 없음. 명시적 이전은 후속 범위 |

위 변경안은 사용자 승인 후 적용했다. 이 범위를 넘어서는 추가 DB 변경은 별도 승인을 받아 결정한다.
