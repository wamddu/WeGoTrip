# 채팅 푸시 및 공통 발송 기반 변경안

상태: 2026-10-25 사용자가 “DB 변경 승인”으로 승인한 후 구현 및 WeGoTrip DB 적용 완료. 기존 채팅 10건을 유지하고 과거 메시지 발송 대기는 생성하지 않았다. 스키마는 `tmp/chat-diagnostics/schema-before-014-1792912857674.sql`에 보관했다. 최종 잠금 충돌 방지 메타데이터 보완 전 신규 테이블 스키마는 `tmp/chat-diagnostics/schema-before-014-final-1792914269515.sql`에 보관했다. 실기기 테스트는 사용자가 “지금은 기기 테스트 없이 마무리”로 생략을 요청했다.

## 범위

새 텍스트·사진·투표 메시지를 작성하면 작성자를 제외한 현재 전체/파티 채팅 멤버의 등록 기기로 FCM 알림을 발송한다. 투표 참여·마감 같은 기존 메시지 수정은 푸시를 만들지 않는다. 기존 계정의 푸시 허용 설정을 존중한다. 알림을 누르면 로그인 및 수신 계정을 확인한 뒤 해당 전체/파티 채팅으로 이동한다.

푸시는 잠금 화면에 대화 원문이나 사진 URL을 포함하지 않는 기본 안내로 제공한다. 실제 대화 내용은 기존 인증 API로 조회한다. 앱 실행 중 수신, 백그라운드 및 종료 상태의 알림 열기 처리를 추가한다.

Firebase 발송 모듈, 발송 대기 처리, 알림 종류별 권한·내용 결정 로직을 분리한다. 이번에는 CHAT_MESSAGE 종류를 연결하며 이후 여행 공지·서비스 공지는 같은 발송 기반에 종류와 수신 대상 정책을 추가할 수 있다. 공지 API와 서비스 관리자 화면은 이번 범위에 포함하지 않는다.

## 승인이 필요한 DB 변경

`014-push-outbox.sql`에서 다음 두 테이블만 추가한다.

| 테이블 | 주요 컬럼 및 제약 |
| --- | --- |
| `push_event` | id, event_type, source_id, actor_id, trip_id(NULL 허용), party_id(NULL 허용), targets_json, expanded_at, created_at, expires_at. 종류·원본 ID 고유 제약으로 같은 채팅 메시지의 중복 작업을 막는다. 대상 스냅샷과 확장 완료 시각으로 채팅 저장 후 기기별 발송 준비를 복구할 수 있다. |
| `push_delivery` | id, event_id, recipient_id, device_id, token_hash, status, attempts, next_attempt_at, lease_until, lease_token, last_error_code, sent_at, created_at. 이벤트·기기 고유 제약 및 대기/재시도/작업 임대 조회 인덱스를 둔다. |

기존 `user_device`와 `user_setting`은 재사용한다. 이벤트와 수신 대상 스냅샷은 원본 채팅 저장과 같은 트랜잭션에서 생성하고, 기기별 발송 대기는 채팅 커밋 후 별도 트랜잭션에서 준비한다. 이는 동시 작성자 간 계정 잠금 충돌을 피하기 위한 구현 보완이다. 원본 채팅·이미지·투표·회원 데이터를 변경하거나 과거 메시지에 대해 소급 발송하지 않는다. 새 테이블은 관련 여행·파티·기기·계정 삭제에 맞춰 외래키로 정리한다.

발송 직전에 현재 여행·파티 멤버십, 계정 상태, 알림 설정, 기기 소유자와 토큰이 유지되는지 확인한다. FCM이 명시적으로 등록 해제됐다고 응답한 기기는 기존 토큰과 일치할 때만 `user_device`에서 제거한다. 새로운 토큰으로 갱신된 기기를 잘못 삭제하지 않는다.

## 발송과 운영

- 백그라운드 작업은 대기 행을 짧은 트랜잭션으로 선점하고, FCM 네트워크 호출은 DB 잠금 밖에서 수행한다.
- 임대 만료 후 작업 복구, 일시 장애 재시도와 지수 간격 증가, 발송 유효기간과 최대 시도 수를 적용한다.
- 성공은 FCM 접수이며 실제 기기 표시를 보장하는 상태는 아니다. 네트워크 응답 유실 같은 경계에서는 중복 알림이 가능하므로 이벤트/기기 ID를 전달하고 클라이언트에서도 중복 표시를 줄인다.
- Firebase 서버 인증은 로컬 ADC 또는 지정한 서버 서비스 계정 파일로 설정한다. 비밀 키·기기 토큰은 로그와 클라이언트에 노출하지 않는다. 인증이 준비되지 않은 환경에서는 채팅 저장은 유지하고 발송은 대기한다.
- 실제 기기에 테스트 알림을 보낼 경우 수신 기기를 먼저 확인한다. 자동화 테스트는 FCM 대역을 사용하고 실제 사용자에게 전송하지 않는다.

## 검증

별도 H2 DB에서 원본 저장과 대기 생성의 원자성, 작성자 제외, 전체/파티 격리, 알림 거절·기기 미등록, 중복 요청, 재시도·임대 만료 복구, 멤버 탈퇴·설정 변경·토큰 갱신 후 차단, 만료 기기 제거를 검사한다. 프런트엔드는 알림 데이터 검증, 계정 일치, 전체/파티 이동, 중복 이벤트와 초기 알림 처리를 검사한다.

실제 DB에는 승인 후에만 테이블을 추가하며, 서버 Firebase 인증과 발송 권한은 별도로 검증한다.
