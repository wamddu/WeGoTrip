# WeGoTrip 정산·준비물 기능 구현 정리

기준일: **2026-10-10**

현재 백엔드·프론트엔드 코드와 기존 구현 기록을 기준으로 정리했다. 지출·정산은 2026-10-02에 서버 저장을 연결했고, 2026-10-09에 수신자 전용 완료 권한을 적용했다. 준비물은 서버 공유 기능에 이어 담당자 전용 체크, 모든 멤버의 개인 항목 생성, 이전 공용 UI 제거까지 반영된 상태다.

## 1. 구현 범위

| 기능 | 현재 동작 |
| --- | --- |
| 지출 기록 | 결제자·금액·날짜·참여자·분담금·소그룹·메모를 등록하고 수정·삭제 |
| 정산 계산 | 여행 전체의 결제액과 부담액을 비교해 송금 대상과 금액 계산 |
| 송금 완료 기록 | 송금을 받는 사람이 입금을 확인한 뒤 완료·취소 상태 저장 |
| 준비물 등록 | 특정 멤버에게 등록하거나 모든 현재 멤버에게 개인 항목을 하나씩 생성 |
| 준비물 체크 | 담당자만 자신의 항목을 체크·해제하고, 모든 멤버가 상태 조회 |
| 공유·갱신 | HTTP 모드에서 서버 데이터를 조회하고 갱신 시 다른 멤버의 변경 반영 |

HTTP 모드는 실제 API를 사용한다. Mock 모드는 샘플 데이터와 기기 저장을 사용하며 실제 DB와 연결되지 않는다.

## 2. 지출 기록과 정산

### 2.1. 지출 등록·수정·삭제

지출 추가 화면에서 금액·제목·날짜를 입력하고 소그룹, 결제자, 함께 부담할 멤버를 선택한다. 분담은 **균등 분할** 또는 **직접 지정**으로 설정한다.

| 입력 | 저장·검증 규칙 |
| --- | --- |
| 제목 | 앞뒤 공백 제거 후 1~150자 |
| 금액 | 1원~10억 원의 정수 |
| 날짜 | 여행 기간 밖 날짜도 허용 |
| 결제자 | 현재 여행 멤버 중 선택. 분담자에 포함되지 않아도 됨 |
| 분담자·금액 | 1~30명, 0원 분담 허용, 분담 합계는 지출 총액과 정확히 일치 |
| 소그룹 | 같은 여행의 소그룹 또는 공동 지출 선택 |
| 메모 | 선택 입력, 최대 1,000자 |

균등 분할은 프론트엔드에서 원 단위로 계산하고 서버가 합계를 검증한다. 나머지는 여행 멤버 순서대로 1원씩 배분한다. 예를 들어 2원을 3명이 나누면 **1원·1원·0원**으로 저장하며, 0원인 멤버도 분담 기록에 남는다.

직접 지정은 멤버별 입력 금액을 저장한다. DB에는 분담 방식 자체보다 **확정된 멤버별 분담금**을 저장한다.

소그룹을 선택하면 해당 소그룹 멤버를 분담자로 기본 선택하지만 이후 변경할 수 있다. 소그룹 필터는 지출 목록에 적용되며, 총 지출과 정산 결과는 여행 전체 기준이다. 소그룹의 이름·구성원만 바꿔도 이미 저장된 분담금은 자동으로 바뀌지 않는다.

### 2.2. 정산 계산

멤버별 잔액은 다음과 같이 계산한다.

```text
잔액 = 내가 결제한 금액 − 내가 부담할 금액
양수: 받을 금액
음수: 보낼 금액
```

**예시: A가 30,000원을 결제하고 A·B·C가 각각 10,000원을 부담하는 경우**

| 멤버 | 결제액 | 부담액 | 잔액 |
| --- | ---: | ---: | ---: |
| A | 30,000원 | 10,000원 | +20,000원 |
| B | 0원 | 10,000원 | −10,000원 |
| C | 0원 | 10,000원 | −10,000원 |

송금 제안은 **B가 A에게 10,000원**, **C가 A에게 10,000원**이다. 이 예시는 기능 설명용이며 실제 DB 내역이 아니다.

서버는 여행 멤버의 고정된 가입 순서로 보낼 사람과 받을 사람을 연결한다. 전체 잔액의 합이 0인지 확인하고, 금액을 임의로 반올림하거나 보정하지 않는다. 모든 경우에 송금 횟수가 최소라고 보장하는 계산 방식은 아니다.

정산 탭은 지출 내역과 정산 결과를 제공하며 총 지출, 내 부담액, 내가 결제한 금액, 멤버별 부담 내역과 송금 상태를 표시한다.

### 2.3. 송금 완료 기록과 권한

완료 표시는 **실제 입금을 확인한 사람이 남기는 수동 기록**이다. 은행 송금이나 자동 입금 확인 기능은 포함하지 않는다.

| B가 A에게 송금해야 하는 경우 | 상태 조회 | 완료 기록·취소 |
| --- | --- | --- |
| A: 송금을 받는 사람 | 가능 | 가능 |
| B: 송금할 사람 | 가능 | 불가 |
| 다른 여행 멤버 | 가능 | 불가 |

화면의 **송금 완료로 기록 / 완료 기록 취소** 버튼은 수신자에게만 표시한다. 서버도 `toUserId`와 현재 사용자를 비교하며, 발신자나 수신자가 아닌 여행장의 요청을 `403 SETTLEMENT_RECEIVER_REQUIRED`로 거절한다. HTTP 저장소와 Mock 모드에도 같은 권한 검증을 적용한다.

이전 정책에서 발신자가 남긴 완료 기록은 조회할 수 있지만, 이후 상태 변경은 수신자만 할 수 있다.

### 2.4. 지출 변경 후 정산 상태

성공한 지출 등록·수정·삭제마다 `trip.settlement_revision`을 증가시킨다. 새로운 정산 버전에서는 송금 제안을 다시 계산하고 완료 상태를 대기로 시작한다.

- 메모·소그룹만 수정하거나 같은 내용으로 저장해도 정산 버전이 증가한다.
- 이전 버전의 완료 기록은 DB에 보존하되 현재 버전 화면에 적용하지 않는다.
- 지출을 변경했다가 원래 내용으로 되돌려도 옛 완료 표시를 되살리지 않는다.
- 소그룹 자체의 이름·구성원 변경만으로는 정산 버전을 증가시키지 않는다.

이 완료 기록은 부분 송금 원장이나 과거 실제 송금액을 자동으로 차감하는 기능이 아니다. 지출을 바꾼 뒤에는 실제 송금 상황을 확인하고 새 정산의 완료 상태를 기록해야 한다.

## 3. 준비물

### 3.1. 특정 멤버 등록과 모든 멤버 등록

준비물 추가 화면의 **누가 준비하나요?** 콤보박스에서 특정 멤버 또는 **모든 멤버가 각자 준비**를 선택한다. 이름은 앞뒤 공백 제거 후 1~150자다.

| 선택 | 생성 결과 |
| --- | --- |
| 특정 멤버 | 해당 멤버가 담당하는 개인 항목 1개 |
| 모든 멤버가 각자 준비 | 등록 당시 현재 활성 멤버마다 개인 항목 1개 |

**4명 여행에 여권을 전체 등록하고 A만 체크한 예시**

| 준비물 | 담당자 | 상태 |
| --- | --- | --- |
| 여권 | A | 완료 |
| 여권 | B | 미완료 |
| 여권 | C | 미완료 |
| 여권 | D | 미완료 |

여권 항목 4개 중 A의 항목만 완료된다. 한 사람이 체크해도 다른 사람의 상태는 바뀌지 않는다. 다른 준비물이 없는 여행이라면 전체 진행률은 **1/4 완료**이며, 기존 준비물이 있으면 그 항목들도 전체 진행률에 포함한다.

서버는 모든 개인 항목을 한 트랜잭션으로 생성하고 신규 완료 상태를 `false`로 저장한다. 같은 이름의 항목을 하나의 완료 상태로 합치거나 별도 그룹 ID로 연결하지 않는다. 등록 이후 합류한 멤버에게 기존 준비물이 자동 생성되지는 않으므로 필요한 항목을 별도로 등록해야 한다.

### 3.2. 완료 권한과 공동 편집

| 작업 | 현재 권한 |
| --- | --- |
| 담당자·완료 상태 조회 | 모든 여행 멤버 |
| 항목 등록 | 모든 여행 멤버 |
| 이름·담당자 수정, 삭제 | 모든 여행 멤버의 공동 관리 |
| 완료 체크·해제 | 해당 항목 담당자 본인만 |

여행장도 다른 사람에게 배정된 준비물을 체크할 수 없다. 다른 담당자의 체크박스는 비활성화하며, 서버는 해당 요청을 `403 PACKING_OWNER_REQUIRED`로 거절한다. HTTP 저장소와 Mock 모드에도 동일한 검증을 적용한다.

수정·삭제는 선택한 **개인 항목 하나**에만 반영한다. A의 여권 이름을 수정하거나 삭제해도 B·C·D의 여권에는 영향을 주지 않는다. 수정 화면은 개인 담당자만 선택할 수 있으며 전체 등록을 다시 실행하지 않는다.

개인 항목의 이름·담당자를 수정할 때는 기존 완료 상태를 유지한다. 담당자가 없는 옛 항목을 API로 개인에게 재배정하는 경우에는 완료 상태를 미완료로 초기화하지만, 현재 화면은 그 옛 항목의 전환 UI를 제공하지 않는다.

### 3.3. 목록·필터·진행률

- **전체 / 내 준비물 / 미완료** 필터를 제공한다.
- **누구의 준비물을 볼까요?** 콤보박스와 멤버별 현황에서 담당자로 좁혀 볼 수 있다.
- 각 항목에 담당자와 완료·미완료 상태를 표시한다.
- 멤버별 완료 수·전체 수·남은 수를 표시한다.
- 미완료를 먼저 보여주고 같은 상태에서는 항목 ID 순서로 정렬한다.
- 목록·여행 개요·홈은 담당자가 있는 개인 항목을 기준으로 집계한다.
- 전체 진행률은 현재 목록 필터와 별개로 모든 개인 항목을 집계한다. 준비물 0개와 모두 완료를 구분한다.

**내 준비물은 공유 목록의 필터**다. 비공개 준비물 공간은 아니며 다른 멤버도 담당자별 상태를 볼 수 있다.

### 3.4. 이전 공용 항목과 담당자 탈퇴

이전의 담당자 없는 단일 공용 항목에 대한 목록·필터·전환 안내·편집 UI는 제거했다. 현재 화면과 진행률은 `ownerId`가 있는 개인 항목만 사용한다.

기존 행이나 담당자 탈퇴로 담당자 FK가 `NULL`인 항목은 DB에 남을 수 있다. API 조회에 포함될 수 있지만 현재 UI는 표시·집계하지 않으며, 완료 요청은 `409 PACKING_ASSIGNMENT_REQUIRED`로 거절한다. 담당자가 탈퇴할 때 기존 완료 상태 자체는 DB에 유지한다.

이전 공용 데이터를 개인 항목으로 자동 변환하거나 일괄 삭제하는 기능은 없다. 이전 작업은 UI 지원 제거였으며 실제 DB 삭제는 사용자가 진행하는 전제였다. 지출·분담·정산 기록이 해당 멤버를 참조하면 기존 참조 보호 정책에 따라 탈퇴가 제한된다.

## 4. DB 저장 구조

| 테이블·컬럼 | 저장하는 내용 |
| --- | --- |
| `expense` | 지출 제목·금액·날짜·결제자·소그룹·메모 |
| `expense_participant` | 지출별 참여 멤버와 분담금 |
| `trip.settlement_revision` | 여행 전체 정산 기준 버전 |
| `settlement_confirmation` | 정산 버전별 송금 완료 상태·행 버전·기록자·시각 |
| `packing_item` | 개인 준비물 이름·담당자·완료 상태 |

API의 `payerId`, 분담금의 사용자 키, `ownerId`, `fromUserId`, `toUserId`는 **사용자 ID**다. 서버가 같은 여행의 멤버인지 검증한 뒤 DB의 `trip_member.id`로 변환한다. API의 ID와 버전은 문자열로 전달한다.

### 정산 완료 기록

`settlement_confirmation`은 `(여행, 정산 버전, 송금자, 수신자)` 조합별 한 행을 저장한다.

| 컬럼 | 의미 |
| --- | --- |
| `trip_id`, `settlement_revision` | 소속 여행과 정산 기준 버전 |
| `from_trip_member_id`, `to_trip_member_id` | 송금자·수신자 |
| `amount`, `completed` | 송금 제안 금액과 완료 여부 |
| `version` | 완료 상태의 동시 변경 검사 버전 |
| `updated_by_trip_member_id`, `updated_at` | 마지막 기록자와 기록 시각 |

지출·정산에는 사용자 승인을 거쳐 `expense.party_id`, `expense.note`, `trip.settlement_revision`과 `settlement_confirmation`을 추가한 기존 009 마이그레이션이 적용돼 있다. 이번 문서 작성에서 DB를 다시 조회하거나 변경하지 않았다.

### 준비물 기록

준비물은 기존 `packing_item(id, trip_id, owner_trip_member_id, title, done)`을 재사용하며 별도 마이그레이션이 없다. 모든 멤버 등록도 이 테이블에 개인 행을 여러 개 생성하는 방식이다.

항목의 `stateToken`은 현재 필드로 계산한 SHA-256 해시이며 DB 컬럼으로 저장하지 않는다. 목록의 `checklistStateToken`은 페이지 사이의 변경을 감지하는 데 사용한다.

## 5. API 연결

공통 경로: `/api/v1/trips/{tripId}`

Bearer JWT 인증과 `{ code, data }` 응답 형식을 사용한다. 조회·변경 응답에는 `Cache-Control: no-store`를 적용한다. **모든 변경 요청에는 UUID 형식의 `Idempotency-Key` 헤더가 필수**다.

| 메서드 | 공통 경로 뒤에 붙는 경로 | 기능 |
| --- | --- | --- |
| GET | `/expenses` | 지출 목록·정산 버전 조회 |
| GET | `/expenses/{expenseId}` | 지출 단건 조회 |
| POST | `/expenses` | 지출·분담금 등록 |
| PUT | `/expenses/{expenseId}` | 지출·분담금 수정 |
| DELETE | `/expenses/{expenseId}?settlementRevision=...` | 기대 정산 버전으로 삭제 |
| GET | `/settlement` | 여행 전체 정산과 완료 상태 조회 |
| PUT | `/settlement/confirmations` | 수신자의 완료·취소 기록 |
| GET | `/packing-items` | 준비물 목록·목록 토큰 조회 |
| GET | `/packing-items/{itemId}` | 준비물 단건 조회 |
| POST | `/packing-items` | 개인 또는 모든 멤버 등록 |
| PUT | `/packing-items/{itemId}` | 이름·담당자 수정 |
| PUT | `/packing-items/{itemId}/completion` | 담당자의 완료·해제 |
| DELETE | `/packing-items/{itemId}?expectedStateToken=...` | 기대 상태 토큰으로 삭제 |

지출 등록·수정의 주요 입력은 `title`, `amount`, `date`, `payerId`, `shares`, `partyId`, `note`이며 수정에는 `settlementRevision`을 추가한다. 정산 조회는 `settlementRevision`, `total`, `balances`, `transfers`를 반환한다.

**수신자의 완료 기록 요청 예시**

```json
{
  "settlementRevision": "1",
  "fromUserId": "102",
  "toUserId": "101",
  "amount": 10000,
  "completed": true,
  "confirmationVersion": "0"
}
```

예시 ID는 실제 데이터와 무관하다. `toUserId`에 해당하는 사용자로 인증하고, 서버가 반환한 현재 송금 제안과 버전을 사용해야 한다. 취소는 최신 `confirmationVersion`과 `completed: false`를 전송한다.

**모든 멤버용 준비물 등록 요청 예시**

```json
{
  "title": "여권",
  "ownerId": null
}
```

여기서 `null`은 모든 멤버 등록 방식이며, 생성 결과에는 각자의 담당자가 지정된다. 등록 응답의 `data`는 **`{ "items": [...] }`** 형태로 개인 등록도 배열을 반환한다. 수정 요청에서는 개인 `ownerId`가 필수이며 `null`을 허용하지 않는다.

준비물 수정은 `title`, `ownerId`, `expectedStateToken`, 완료 변경은 `done`, `expectedStateToken`을 전송한다. 완료 여부는 토글 명령이 아닌 목표 상태인 boolean으로 전달한다.

## 6. 보관·재시도·동시 수정

### 보관 여행의 권한

| 기능 | 보관 후 조회 | 보관 후 새 변경 |
| --- | --- | --- |
| 지출 | 가능 | 등록·수정·삭제 불가 |
| 정산 | 가능 | 수신자의 완료·취소 가능 |
| 준비물 | 가능 | 등록·수정·체크·삭제 불가 |

이미 성공한 동일 요청의 재확인은 새 변경과 구분하며 현재 접근·담당자 권한을 검사한다.

### 공통 안정성 처리

- **중복 저장 방지:** 같은 키·입력을 재전송하면 최초 성공 응답을 반환한다. 같은 키에 다른 입력을 보내면 `409 IDEMPOTENCY_KEY_REUSED`로 거절한다.
- **트랜잭션:** 지출·분담금·정산 버전과, 전체 준비물 등록의 여러 개인 행을 각각 중복 요청 결과와 함께 저장한다. 중간 실패 시 해당 작업 전체를 롤백한다.
- **동시 수정 검사:** 지출은 `settlementRevision`, 송금 완료는 정산 버전과 `confirmationVersion`, 준비물은 `expectedStateToken`을 검사한다.
- **현재 권한 재검사:** 완료 요청의 재시도에서도 수신자·담당자 권한을 확인한다. 준비물 담당자가 바뀌면 이전 담당자의 완료 요청 재시도도 차단한다.
- **충돌 처리:** 최신 데이터를 반영하고 입력 초안을 유지한다. 오래된 내용의 자동 덮어쓰기나 삭제된 항목의 자동 재생성은 하지 않는다.
- **응답 유실:** 원래 키·입력·버전을 유지해 명시적으로 재시도한다. 준비물은 저장 성공이 확인되고 조회만 실패하면 조회만 재시도한다. 지출·정산은 원래 키로 요청을 다시 보내 서버의 중복 요청 처리로 중복 변경을 막는다.
- **재시도 만료:** 중복 요청 보관 기간은 24시간이다. 확인되지 않은 오래된 요청은 자동 재전송하지 않고 최신 목록 확인을 안내한다.
- **목록 일관성:** 페이지 사이에 변경이 생기면 최초를 포함해 총 최대 3회 조회를 시도하고, 완전한 결과만 화면에 반영한다. 실패를 빈 목록으로 표시하지 않는다.

| 주요 오류 | 의미 |
| --- | --- |
| `403 SETTLEMENT_RECEIVER_REQUIRED` | 송금 수신자만 완료·취소 가능 |
| `403 PACKING_OWNER_REQUIRED` | 준비물 담당자만 완료·해제 가능 |
| `409 SETTLEMENT_CHANGED` | 지출·정산 기준 버전 충돌 |
| `409 CONFIRMATION_CHANGED` | 송금 완료 행 버전 충돌 |
| `409 PACKING_ITEM_CONFLICT` | 준비물 항목 상태 충돌 |
| `409 PACKING_LIST_CHANGED` | 준비물 페이지 조회 중 목록 변경 |
| `409 TRIP_ARCHIVED` | 보관 여행의 새 지출·준비물 변경 제한 |

`PACKING_ASSIGNMENT_REQUIRED`는 수정 시 담당자를 지정하지 않으면 400, 담당자 없는 항목의 완료나 옛 공용 응답 재사용은 409로 반환한다.

## 7. 공유 데이터 갱신과 기기 기록

탭 진입·앱 복귀·새로고침·변경 성공 시 서버 데이터를 다시 조회한다. 다른 기기의 변경은 이 갱신 시점에 반영되며 실시간 푸시 동기화는 아니다.

기존 기기 기록은 `expense-backup-v1`, `checklist-backup-v1` 계열의 별도 저장 키로 보존한다. HTTP 모드에서는 서버 결과를 사용하며 기기 기록을 자동 업로드하거나 합치지 않는다. 기존 자료의 명시적 가져오기 UI는 이번 범위에 포함하지 않았다.

현재 지출·정산·준비물은 서버 공유 대상이며 공지·대화의 기존 기기 저장 방식은 유지한다.
