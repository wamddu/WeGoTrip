# 여행 내 소그룹(파티)

파티는 여행 멤버 일부를 묶는 소그룹이다. 특정 날짜나 시간에 종속되지 않으며, 같은 파티를 여행 기간의 여러 날짜 일정과 지출에 선택할 수 있다.

## DB와 변경 범위

연결된 MySQL의 테이블·컬럼·외래키를 읽기 전용으로 확인했다. 기존 `trip_party(id, trip_id, name, created_at)`와 `trip_party_member(id, party_id, trip_member_id)`를 그대로 사용한다. DB 스키마 변경이나 운영 데이터 수정은 수행하지 않았다.

`memberIds`는 API와 화면에서는 사용자 ID이고, 저장할 때 해당 여행의 `trip_member.id`로 변환한다. 파티 멤버는 현재 여행 멤버만 가능하다. 기존 DB의 중복 방지 제약과 멤버 삭제 시 CASCADE를 사용한다.

UI는 승인받은 파티 날짜·시간 입력/표시 제거와 저장 안내 문구만 변경했다. 이름·멤버 선택, 저장·수정·삭제, 파티별 일정 화면의 디자인과 배치는 유지한다. 일정 자체의 날짜·시간은 계속 사용한다.

## API

모든 경로는 `/api/v1/trips/{tripId}/parties` 아래에 있으며 기존 인증 토큰과 응답 envelope를 사용한다.

| 메서드 | 경로 | 동작 |
| --- | --- | --- |
| GET | `/` | `cursor`, `limit` 기반 목록 조회 |
| GET | `/{partyId}` | 파티 조회 |
| POST | `/` | 이름·멤버로 파티 생성. UUID `Idempotency-Key` 필수 |
| PUT | `/{partyId}` | 이름·멤버 전체 갱신 |
| DELETE | `/{partyId}` | 파티와 소속 멤버 연결 삭제 |

생성·수정 본문:

```json
{ "name": "카페팀", "memberIds": ["1", "2"] }
```

응답 파티에는 `id`, `name`, `memberIds`, `createdAt`이 있다. 이름은 공백 제거 후 1~50자이며, 멤버는 중복 없이 1~30명이다. 여행 멤버라면 파티를 관리할 수 있다. 여행 비참여자에게는 404, 미인증·폐기된 토큰에는 401을 반환한다. 보관 여행은 조회만 가능하다.

쓰기 작업은 트랜잭션과 여행 행 잠금으로 묶인다. 생성 재시도는 기존 `api_idempotency` 테이블을 사용해 24시간 동안 같은 요청의 중복 생성을 막는다. 다른 입력에 같은 키를 사용하면 409를 반환한다. DB 일정(`itinerary_item`)에 연결된 파티의 삭제는 409로 차단한다.

## 프론트엔드 연결

HTTP 저장소는 파티 목록을 서버에서 가져오며 기존 편집 명령을 위 API에 연결한다. 생성 성공 후 서버 ID로 다시 불러온다. 응답 유실이나 재조회 실패 시에도 같은 생성 요청 키를 사용한다. 다른 계정·기기에서는 목록 새로고침 또는 관리 화면 재진입 시 변경 사항을 확인할 수 있다.

예전 기기 저장소의 파티는 서버로 자동 업로드하지 않고 원본을 보존한다. 서버 파티를 로컬 데이터로 덮어쓰지 않는다. 예전 로컬 파티에 연결된 일정·지출은 자동 이관하지 않으므로 새 서버 파티로 다시 연결해야 한다. 일정·지출 자체는 이번 구현에서도 기기별 저장이며, 현재 기기의 일정·지출에 연결된 파티 삭제도 기존 검증으로 차단한다. 다른 기기의 로컬 일정·지출은 서버가 검사할 수 없다.

## 검증 및 실행

- `backend`: `./gradlew.bat test` — 기존 API와 파티 API 통합 테스트. 파티용 테스트 스키마는 실제 테이블을 재현하는 별도의 H2 메모리 DB 전용이다.
- `frontend`: `npm run typecheck`, `npm test` — 소그룹의 여러 날짜 일정, 서버 CRUD, 계정 전환, 기존 기기 데이터 보존, 응답 유실 재시도 검증.

실행 중인 백엔드는 새 API를 반영하도록 재시작해야 한다. DB 마이그레이션은 필요하지 않다. 프론트엔드와 백엔드 코드는 함께 반영해야 한다.
